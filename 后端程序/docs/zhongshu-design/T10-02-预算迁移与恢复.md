## 1. 复用与改动边界

- 新迁移 `V20260908.207__t10_itemized_budget.sql`，旧 `201～206` 保持原文件，不改校验和。
- 继续以 `budget_estimate` 作为唯一预算主表。增加模型、保存标志、当前修订和生成幂等字段；不新建预算主表或收藏关系。
- 新建 `budget_region / budget_item / budget_option / budget_item_price / budget_revision / budget_line / budget_quote`，分别承载地区、目录、价表和项目快照，不建立通用公式、流程或审计引擎。
- 既有 `design_requirement_snapshot.inputs` 继续存设计输入；既有 `audit_event` / `AuditPort` 继续负责业务审计，本批没有另建参数表或审计表。
- 仅种入禁用且未开放用户选择的 3+7 个标准项目录身份；不写地区、选项、价格或客户数据。自定义模板默认不向用户开放。

## 2. 新旧兼容

旧行默认 `LEGACY_RANGE`，原规则ID、上下限、输入、时间及免责声明逐字段保留，不计算中值、不虚构明细。旧形状 INSERT 仍可用。

`ITEMIZED_V1` 主记录不得写旧区间字段，必须和首个修订在同一事务创建。延迟外键保证事务提交时当前修订实际存在；修订绑定本预算和租户。保存标志不重新计算金额。

本批兼容服务只读取 `LEGACY_RANGE`，不会把新行的 NULL 金额解码为 0。T10-06 完成新模型 DTO 后，原详情/列表入口再按模型分流；此之前不能开放新建分项预算，也不能手工写测试预算冒充可用业务。

旧创建入口现在复用 `DesignProjectService.getProject(projectId, userId)` 校验项目；关联方案必须属于同一项目且未删除。旧详情和项目列表也检查当前归属。响应添加模型字段，原字符串ID和金额字段不变；金额字段文档单位修正为分。

## 3. 数据库约束与服务职责

数据库已表达：

- 目录身份唯一、跨租户/跨选项引用限制、同修订行键/选项去重。
- 金额为整数分，非负且有上限；数量使用 NUMERIC 并显式限制4位精度，避免 NUMERIC(p,4) 静默舍入非法输入。
- 个/套/户/项必须整数；缺价 NULL 与有原因的免费 0 不同。
- 五种行状态、逐行四舍五入金额、两分类小计之和、完整预算总额/不完整总额 NULL。
- 报价必须引用同一预算的 COMPLETE 修订和相同系统总额，最终金额等于系统额加调整额；发布/撤回元数据必需。
- 生成、修订、报价创建分别有业务唯一键；当前修订的引用不能悬空。

以下必须在后续事务服务实现并测试，**不是本迁移已完成的能力**：

- 同地区选项价格有效区间互斥：锁地区行，检查 `[effective_at, expires_at)` 重叠；未引入 PostgreSQL 扩展。
- 核心编码不可修改、已发布价/旧快照不可变、数量来源与选项选择组合法性。
- 对实际行汇总并判断完整性；空明细不可标 COMPLETE。数据库 CHECK 不能代替跨行汇总。
- 同幂等键请求指纹一致性、发布/撤回重试、预期版本竞争、写操作权限、审计同事务、公开字段白名单。
- 只读权限与跨项目数据范围校验。新表存在不表示 Admin/App API 已开放。

## 4. 验证方法

沿用仓库 JDK 17、Maven Wrapper、PostgreSQL 17 Testcontainers/Flyway，不使用 H2/SQLite 替代。命令在 `后端程序` 执行（本机 JAVA_HOME、Maven 缓存路径不写入项目配置）：

```powershell
.\mvnw.cmd -B '-Dtest=BudgetLegacyT10ContractTest' '-Dsurefire.failIfNoSpecifiedTests=false' -pl yudao-module-design -am test
.\mvnw.cmd -B '-Dtest=BudgetSchemaT10ContractTest,BudgetMessageP7BContractTest' '-Dsurefire.failIfNoSpecifiedTests=false' -pl yudao-module-design -am test
```

第一组只测预算查询前的归属/面积拒绝以及旧响应映射；不伪装成数据库测试。

第二组在一次性 PostgreSQL 容器独立 schema 验证空库迁移、迁移重复执行、旧库升级逐字段不变、新旧形状、延迟外键、事务失败回滚、缺价/免费/精度、报价引用、目录和旧接口归属。已有 P7B 测试继续验证旧预算调价历史不漂移和消息链。失败清理仅限测试容器，不 TRUNCATE 共享开发库。

标准入口 `node scripts/verify.mjs backend` 的 `*ContractTest` 会发现两份新测试；测试资产统计已增量更新，统计数不代表通过数。

## 5. 升级及恢复顺序

1. 先在一次性测试库执行上述两组测试，再在隔离的旧库备份副本验证升级；记录迁移历史、旧预算行数及快照/上下限摘要。生产执行另需授权、备份与维护窗口。
2. 先部署兼容版本：旧读取按模型过滤，新分项入口保持未开放。数据库迁移成功后旧预算业务继续使用原区间规则。
3. PostgreSQL/Flyway 本迁移按事务执行；若语法/约束导致迁移失败，先确认事务回滚及 `flyway_schema_history` 状态。未验证前不启动依赖新结构的版本。
4. 失败恢复演练由测试中的明细冲突触发整笔主记录/修订回滚，并断言旧预算仍可读取。真实环境不能以删库、清表或直接 `repair` 跳过失败来验收。
5. 迁移一旦在正式环境成功应用，不再编辑文件；发现问题以新版本前向修复。已产生新预算后只回退到**支持模型隔离的兼容版本**，停止新写入但保留新旧历史；不能回退到会把 NULL 读作0的原始代码。
6. 本批尚无业务停用开关或新模型读取服务，故不能作为 T10-19 的完整应用回滚演练通过证据。不得 DROP 新表、删除已发布报价或把新金额填回旧区间列。
