# T13-04 真实微信身份适配器（code2session）V1.0

日期：2026-09-09。所属批次：B1（微信身份与激活入口）。对应任务：T13 计划 §5 B1 表 T13-04。

验收标准（计划原文）：**实现真实 WechatIdentityPort｜服务端 code2session，只接受客户端临时 code；appid 来自配置；不接受客户端 openid，不将 session_key 返回前端。**

本文是 B1 真实微信身份适配器的**开发交付记录**。它证明「真实 `code2session` 适配器已实现并被隔离测试覆盖」，**不**代表已在真实微信环境验收通过——真实验收属凭据依赖项，见 §6 与《T13-03》§4.1。

## 1. 目的与边界

- **目的**：把 `WechatIdentityPort` 的开发替身（`StubWechatIdentityAdapter`，SHA-256 派生假 openid）替换为**真实服务端 `code2session`**：用小程序 `wx.login` 得到的临时 `code`，在服务端携带 `appid`+`appsecret` 向微信换取 `openid`/`unionid`，领域模型（`WechatSession`）与消费方（`AccountLoginService`）不变。
- **边界（本文不声称）**：
  - 隔离测试通过 ≠ 真实微信渠道可用；真实 `code2session` 联调需公司注入正式 `AppID`/`AppSecret`（§6）。
  - 本项**不**改动登录错误分类、超时策略与登录链路错误处理——那是 **T13-05** 的范围（本文只落地适配器本体与其固有健壮性）。
  - 装配仍由 T13-01 的 `provider` 键驱动，默认 `stub`；本项**不**改变任何环境的默认装配（切 `real` 需显式配置 + 注入密钥）。

## 2. 实现：`RealWechatIdentityAdapter`

新增 `后端程序/yudao-module-identity/.../wechat/RealWechatIdentityAdapter.java`，与 `StubWechatIdentityAdapter` **互斥装配**：

| 维度 | 实现 |
|---|---|
| 装配条件 | `@ConditionalOnProperty(prefix="zhongshu.identity.wechat", name="provider", havingValue="real")`（stub 适配器为 `havingValue="stub"`，二者不可能同时装配） |
| HTTP 客户端 | JDK `java.net.http.HttpClient`（零新依赖，与 T13-03 `FakeHttpServer` 测试端一致）；`connectTimeout` 限制建连、`HttpRequest.timeout` 限制至响应头时间；**`sendAsync().get(totalDeadline)` 界定「建连+响应头+body 读取」完整交换硬上限**（兜底 Java 17 下 `HttpRequest.timeout` 收到响应头即失效、不限时 body 读取的缺口）；`Redirect.NEVER` 禁止跟随重定向；**静态块设 `jdk.httpclient.disableRetryConnect=true`** 关闭 JDK 对连接失败的内部自动重发（尊重外部已设值），避免重复投递一次性 code；**另有包级构造器供隔离测试注入替身 `HttpClient`**（确定性验证超时/`cancel` 路径），故本类有两个构造器——Spring 装配构造器标 `@Autowired` 显式消歧，否则多构造器下 Spring 会回退寻找无参构造器而实例化失败 |
| 端点 | `GET {base-url}/sns/jscode2session?appid=&secret=&js_code=&grant_type=authorization_code`；`base-url` 可配置（默认 `https://api.weixin.qq.com`），隔离测试指向本地假服务器；**畸形 `base-url` 在构造期即快速失败**——`URI.create` 后校验 scheme 必为 http/https、`getHost()` 非空（拦截下划线主机名 `bad_host` 等 registry-authority）、不含 query/fragment（此时未拼入 secret/code，异常只含 base-url）；请求期以字符串拼接 + `URI.create` 构建完整 URI（`baseUri.resolve("?...")` 对仅查询串的相对引用会丢失基址路径，故不用），并把 `URI.create + HttpRequest.newBuilder + build` 整条链包进 `try/catch`，任何 `RuntimeException` 转成「不含 URL、不含 cause」的净化异常（`HttpRequest.newBuilder(uri)` 会二次校验 URI，其异常消息含带 secret+code 的完整 URL，故必须与 `URI.create` 同处一个 try 内） |
| 凭据来源 | `appid` 由调用方 `AppAuthController`（`@Value zhongshu.identity.wechat-appid`）作为**方法入参**传入；`appsecret` 仅存服务端配置 `zhongshu.identity.wechat-appsecret`（构造器 `@Value` 注入） |
| JSON 解析 | **专用 `ObjectMapper`**（不复用 `JsonUtils.parseObject`——后者解析失败会 `log.error` 完整响应体，而微信成功响应含 `session_key`），关闭 `FAIL_ON_UNKNOWN_PROPERTIES` |

### 2.1 安全边界（对应验收四要点）

1. **只接受客户端临时 code**：入口 `AppAuthLoginReqVO` 只有 `code`（`@NotBlank`）字段，类型层面即无 openid；适配器只把 `code` 作为 `js_code` 上送微信。
2. **appid 来自配置**：`appid` 源自 `zhongshu.identity.wechat-appid`（经控制器入参），客户端无从篡改。
3. **不接受客户端 openid**：openid 只来自微信响应，绝不来自请求体。
4. **不将 session_key 返回前端**：响应 DTO `Code2SessionResponse(openid, unionid, errcode)` **刻意不含 `session_key`，亦不含 `errmsg`**——Jackson 忽略未知字段，`session_key`/`errmsg` 从不进入对象图；返回类型 `WechatSession(openid, unionid)` 亦无该字段。三重保证：不解析、不保留、类型上无法返回。（`errmsg` 是微信返回的不可信文本，可能回显 `js_code`/`secret`/URL，故不解析保留、不外泄；错误分类改由数值 `errcode` 承担，见 T13-05。）

### 2.2 固有健壮性（T13-05 将细化分类与链路处理）

- **有界总超时**：建连/至响应头分别限时（默认 3000ms/5000ms，可配 `connect-timeout-ms`/`read-timeout-ms`），并以 `sendAsync().get(connect+read)` 强制「完整交换（含 body 读取）」硬上限——服务端发完响应头再停滞 body 也无法无限挂起请求线程；超时即 `future.cancel(true)` 释放底层交换，`ExecutionException` 中 `HttpTimeoutException` 根因归一为同一「请求超时」语义（便于 T13-05 分类）。
- **一次性 code 不重试**：`code2session` 应用层单次调用，任何失败立即抛出不再发（重试同一 code 只会得到「已使用」并掩盖真实故障）；并以 `disableRetryConnect=true` 关闭 JDK HttpClient 对连接失败的内部自动重发。
- **异常无 cause、消息净化**：`WechatIdentityException` **刻意不提供携带 cause 的构造器**，从类型层面杜绝把底层 Jackson/IO 异常（其消息可能回显响应体片段或含 secret+code 的完整 URL）作为 cause 外抛——否则经 `GlobalExceptionHandler` 的 `rootCauseMessage`/`stackTrace` 落入错误日志库。日志与异常消息**只含数值 `errcode` 与异常类型名**，绝不含 `errmsg`、`secret`、`js_code`、`session_key` 或完整请求 URL；适配器只把「异常类型名」写进日志格式化消息、**绝不把异常对象交给 logger**，故 logback 渲染 stacktrace 时也不存在泄露含凭据 cause 的路径。
- 失败统一抛 `WechatIdentityException`（携带微信 `errcode`，非业务错误时为 `null`），供 T13-05 在登录链路映射为不同错误码。

### 2.3 框架日志脱敏（codex 七轮加固）

登录 `code` 属一次性凭据，但会随请求体 / 查询参数流经框架的**三处**持久化日志点：`ApiAccessLogInterceptor`（非 prod 控制台）、`GlobalExceptionHandler.buildExceptionLog`（全环境错误日志库的 `requestParams`）与 `ApiAccessLogFilter`（访问日志库的 `requestParams`）。为此新增通用工具 **`SensitiveLogRedactor`**（`yudao-spring-boot-starter-web` 的 `web.core.util`），在写入这些日志前遮蔽凭据类字段值（`code`/`password`/`secret`/`token`/`session_key` 等），三处共用同一份敏感键「单一事实源」：

- **改用 JSON 解析器结构化遮蔽，而非正则**（首轮正则实现被 codex 证伪）：正则会漏遮 unicode 转义键（`{"co\u0064e":...}` 实为 `code`）、被值内转义引号截断（`{"password":"a\"SECRET"}` 泄露 `SECRET`）、把 `promo-code` 等形近键过度遮蔽、还会把逗号误当分隔符。现方案把 JSON 解析为树、递归将敏感键的值**不论类型**（字符串/数值/布尔/对象/数组）整体替换为 `***`（Jackson 已解码键的 unicode 转义、已解析值的转义引号，无绕过；**数值型凭据如 `{"password":12345678}` 亦被遮蔽**，因 Jackson 会把不带引号的 JSON 数值绑进 VO 的 String 字段），**非 JSON 或畸形 JSON（含缺左括号）一律整体省略**为 `[omitted-unparseable]`（绝不回显可能含凭据的原文）；
- 查询参数 / 表单键值（`getParamMap` 的 `Map`，键已由容器 URL 解码）走 `redactMap` 逐键（大小写不敏感）完整遮蔽、返回新 Map 不改入参；请求体只按 JSON 处理（`redactJsonBody`），**非 JSON 文本（表单串、缺左括号畸形 JSON 等）不再走有缺陷的正则、而是一律整体省略**（消除逗号误判、URL 编码键漏匹配、`promo-code` 过度遮蔽等缺陷）；
- 键名精确匹配（大小写不敏感），`barcode`/`zipcode`/`promo-code` 等形近键不误伤；**`ApiAccessLogFilter` 的敏感键匹配同步改为大小写不敏感**（原 `ArrayUtil.contains`/`MapUtil.removeAny` 精确匹配会漏移除 `CODE`/`Session_Key` 等大写变体）——三处日志点共用 `SensitiveLogRedactor.isSensitiveKey` 单一判定；响应态整数状态码由 filter 的 `CommonResult` 分支（只处理 `data`、跳过 `code`/`msg`）单独保障，不经 `redactJsonBody`；
- **专用 `ObjectMapper` 从不记录输入**（区别于 `JsonUtils.parseTree`——后者解析失败会 `log.error` 原文，反而泄露；故 `ApiAccessLogFilter` 的 body 脱敏也改用它）；
- **请求体解析异常脱敏**（codex 四轮）：畸形 JSON 请求体（如 `{"code":LOGINSECRET}` 未加引号）会触发 `HttpMessageNotReadableException`，其 `message`/`rootCauseMessage`/`stackTrace` 文本回显原始请求体 token（`Unrecognized token 'LOGINSECRET'`），构成 `requestParams` 之外的**独立泄露向量**（经 `GlobalExceptionHandler.buildExceptionLog` 落错误日志库，并被 `log.warn`/`log.error` 打印原始 throwable）。新增 `SensitiveLogRedactor.isBodyParseLeak(Throwable)`（以 BFS 同时遍历 `cause` 链与 `suppressed` 异常，识别 Spring `HttpMessageNotReadableException` 与 Jackson `JsonProcessingException`；入队即 identity 去重杜绝任意环、遍历预算只对「不同节点」计数、耗尽则保守视为泄露而触发省略——codex 五轮修正原「仅走 cause、深度上限 32、不查 suppressed」的漏判，六轮再把去重从出队前移到入队、使重复引用不再虚耗预算而误判过度脱敏，七轮把节点上限判定移到入队前（`visited.size()` 逾 `MAX_DISTINCT_NODES` 即时返回）以有界化队列与 visited 集合、杜绝海量不同 `suppressed` 一次性撑大辅助集合（可观察 true/false 语义不变））：命中时 `buildExceptionLog` 把上述三个异常文本字段整体替换为安全占位符 `[omitted-body-parse]`（仅保留异常类型名与栈帧位置元数据），`methodArgumentTypeInvalidFormatExceptionHandler`/`defaultExceptionHandler` **不再把原始 throwable 交给 logger**（仅记录类型名）、并**返回固定 400 不回显 `InvalidFormatException.getValue()`**；
- **访问日志库异常文本脱敏**（codex 五轮，修 P1）：`ApiAccessLogFilter` 在下游 filter chain 于 `CommonResult` 记录前抛出请求体解析异常时，会把 `ExceptionUtil.getRootCauseMessage(ex)` 原文写入访问日志库的 `resultMsg`——这是**独立于错误日志库路径**的凭据泄露向量（即便 `requestParams` 已脱敏仍会泄露）。现同样以 `isBodyParseLeak(ex)` 判定，命中即替换为 `[omitted-body-parse]`；非解析异常（普通 `RuntimeException`）仍保留其 `rootCauseMessage` 以便正常排障（不过度脱敏）。
- **空栈帧仍安全落库**（codex 五轮，修 P2）：`buildExceptionLog` 原以 `Assert.notEmpty(stackTraceElements)` 断言栈帧非空，当异常栈被清空（`setStackTrace(new StackTraceElement[0])`）时会抛异常被 `createExceptionLog` 的 catch 吞掉、导致整条错误日志 DTO 不落库（丢失审计记录）。现改为：有栈帧取首帧位置元数据；无栈帧用安全占位（类名回退为异常类名、`file`/`method`=`unknown`、行号 `-1`）**继续落库**，绝不因缺帧丢审计；
- **仅用于日志输出**，`ServletUtils.getBody` 交给反序列化的原始请求体不受影响，不改变任何业务语义。

## 4. 启动守卫登记（复用 T13-02 校验）

`RealServiceWiringPolicy.REAL_MODE_REQUIREMENTS` 追加一条：`provider=real` 时要求 `zhongshu.identity.wechat-appsecret` 非空。AppSecret **无开发占位值**（zsdev 默认留空），故 `placeholderValue=null`——`validate()` 仅校验非空（`value.equals(null)` 恒 `false`，自动跳过占位值比对）。至此「启用真实微信身份才要求 appid+appsecret」由启动守卫强制：缺失即启动期快速失败，早于运行期 code2session 失败，且违例消息只回显键名/环境变量名。

### 5.1 `RealWechatIdentityAdapterTest`（identity 模块，18 用例，全绿）

全程把 `base-url` 指向 T13-03 的 `FakeHttpServer`（绑定 `127.0.0.1` 临时端口），直接 `new` 适配器（构造器注入），**绝不触达真实微信、不产生任何真实调用**；并用 logback `ListAppender` 捕获适配器 logger 的**实际输出**，以证明「敏感值从不落日志」而非仅凭代码走查；除断言消息/cause/日志文本不含敏感值外，另以 `ThrowableProxyUtil.asString` 渲染完整 stacktrace、并断言所有日志事件**均不附带 throwable**（根因级杜绝 stacktrace 泄露含凭据 cause）；确定性超时用例经包级构造器注入 Mockito 替身 `HttpClient`（永不完成的 `sendAsync` future）稳定触发 `cancel`；类级 `@Timeout(30s, SEPARATE_THREAD)` 防任何用例挂起：

| 用例 | 断言要点 |
|---|---|
| 成功映射 | `openid`/`unionid` 正确；请求查询串含 `appid`/`secret`/`js_code`/`grant_type`；返回对象 `toString()` 与**日志**均不含 `session_key` |

| errcode 40029（无效 code） | 抛 `WechatIdentityException`，消息含 `40029`、**不含 errmsg**「invalid code」/secret/code/session_key；**`hasNoCause()`**；日志只含 `40029` |
| errcode 透传 | `getErrcode()` 携带微信原始码（如 40163 已使用）；消息不含 errmsg |
| errcode -1（系统繁忙）**不重试** | 抛出后假服务器**只收到 1 次请求** |
| HTTP 500 | 抛出，消息含状态码，**不泄露响应体**，`hasNoCause()` |
| **畸形 JSON 内嵌全部敏感值** | 抛「解析失败」；消息/`cause`(null)/日志**三处均不含** secret/code/session_key（证 Jackson source 不外泄） |

| **errmsg 回显凭据** | 即便微信 errmsg 内嵌 code/secret/session_key，异常消息与日志**均不出现**（record 无 errmsg 字段） |
| errcode=0 却缺 openid | 抛「协议异常」 |
| appsecret 空 / appid 空 / code 空 | **发起任何 HTTP 调用之前**即失败（假服务器零请求） |
| **传输失败（`stubCloseWithoutResponse`）** | 经假服务器注入「接受后直接关连接」→ 净化异常，消息不含 URL/secret/code，`hasNoCause()`，日志不泄露 |
| **畸形 base-url（含空格）** | 构造期 `URI.create` 即 `IllegalArgumentException`（未拼入 secret/code），异常不含 secret，零请求 |
| **畸形 base-url 三变体** | 下划线主机名 `bad_host`（`getHost()`=null）/ 自带 query `?x=1`（`getQuery()`≠null）/ `ftp://`（scheme 非法）均在**构造期**即 `IllegalArgumentException`，绝不推迟到请求期由 `HttpRequest.newBuilder` 抛出含完整凭据 URL 的异常 |
| **完整交换硬上限确定性 `cancel`** | 注入永不完成的 `sendAsync` future（Mockito 替身 `HttpClient`）→ `future.get(totalDeadline)` 必然超时 → 断言抛「超时」、`hasNoCause()`、且 `future.isCancelled()` 为真（确定性证明 `cancel(true)` 释放，不依赖 JDK 对 header-timeout / total-deadline 何者先触发的版本差异） |
| **停滞响应体（`stubStalledBody` 5000ms）** | 完整交换硬上限 700ms 触发「超时」并 `cancel` 释放，实测 `elapsedMs<3000` 证线程未被挂起 |
