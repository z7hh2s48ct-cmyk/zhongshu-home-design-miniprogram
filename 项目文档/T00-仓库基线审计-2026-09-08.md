## 1. 结论

**准入结论：有条件 GO。**

本仓库已经具备正式拆分任务所需的业务边界、三端源码和详细领域文档，可以进入任务拆分；但当前只适合作为“源码归档与规划基线”，还不能作为“可持续构建、可复验、可生产发布”的工程基线。

正式拆分后的第一批任务必须先解决基线可追溯、根级 CI、E2E 证据归档、管理端锁文件、小程序发布包体及生产配置问题。真实微信、支付、对象存储、AI Provider、内容审核和生产运维必须作为独立门禁，不得被当前 Stub 链路的通过结果替代。

当前工作树在审计开始时干净，远端为 `origin/main`。仓库共有 9,146 个受控文件、约 56 MiB 工作树内容（不含 `.git`）：

| 区域 | 文件数 | 体积 | 角色 |

| `后端程序/` | 8,338 | 42.93 MiB | RuoYi-Vue-Pro/JDK 17 单体后端、平台底座、四个众墅业务模块、SQL 与文档 |
| `管理后台/` | 578 | 5.39 MiB | Vue 3 + Vite + Element Plus 管理端 |

根目录职责清楚，但缺少根级工程编排：无根级 CI、统一启动脚本、统一测试入口、环境自检脚本、版本矩阵、贡献规范和发布说明。

### 2.1 可追溯性

- 当前 Git 历史只有 1 个无父提交的归档提交。
- 根 README 登记的三端来源 SHA 均未包含在当前对象库中，无法执行 `git show`、`git blame`、差异审计或回滚：
  - 小程序：`be57fed0cac613e7272cdb7dba24c557304f3361`
  - 管理端：`a6969959bc41a8bb087bd95c4aa58fadd518ad11`

因此当前能证明“文件快照是什么”，不能证明“这些文件如何演进到这里”。正式多人协作前，应导入三端历史、保留只读来源仓库，或至少建立带来源 URL、分支、SHA、树哈希与归档签字的 provenance 清单。

## 3. 三端代码审计

### 3.1 微信小程序

**已具备**

- 原生小程序结构完整，`app.json` 注册 17 条页面路由和 4 个自定义 Tab。
- `utils/api.js` 已封装身份、授权、案例、收藏、两阶段设计、AI 任务、充值、点数、消息和隐私等 API。
- 草图上传、候选选择、结果版本、预算、投稿、充值查询等主流程已有真实 API 接线。
- 门禁代码集中在 `utils/access.js`，结构测试覆盖页面路由、事件绑定、素材引用和授权行为。

**未完成或不满足发布**

1. `project.config.json` 仍使用 `touristappid`，`utils/config.js` 仍硬编码 `http://localhost:48080` 和 `env: dev`，没有可审计的多环境发布配置。
2. `auth/index.js` 内置 `DEMO-ONLY` 本地放行码。即使注释声明“正式环境走真实接口”，代码本身没有构建时强制剔除或生产断言。
3. “我的方案、户型投稿、收藏户型、充值记录、设置”五个入口仍统一调用 `showPlaceholder()`，明确提示“功能建设中”。“上传参考图片”也标记“即将开放”。
4. `miniprogram/` 为 6.69 MiB，其中 `assets/v12/` 为 6.01 MiB，且未配置分包；单张 `home-hero-scene.png` 约 1.87 MiB。按仓内部署文档既定的主包目标，当前不能直接作为正式上传包，必须迁移业务图片到 COS/CDN 或实施分包和压缩。
5. 当前测试主要验证静态结构与门禁行为，没有小程序运行时、真机、网络异常、支付拉起和视觉回归证据。

**完成度判断**

- 页面与 API 接线：约 **80%～85%**。
- 正式发布准备：约 **45%～55%**。
- 可用于 Stub 内测，但不能据此认定已完成真机、真实身份、真实支付或真实 AI 生成。

### 3.2 管理后台

**已具备**

- `src/views/zs/` 有 15 个业务 Vue 页面文件：工作台、案例新增/列表、审核列表/详情、授权码/批量发码、充值方案列表/编辑、订单、点数流水、C 端用户、AI 任务、导出、审计。
- `src/api/zs/index.ts` 提供 38 个导出请求方法；后端存在相应的管理端控制器与权限点。
- 静态路由覆盖业务页面，登录页、标题、Logo 等已做品牌化。

**未完成或存在风险**

1. `package.json` 没有任何单测脚本，仓内也没有管理端测试文件。
2. 本机执行 `pnpm install --offline --frozen-lockfile` 时，供应链校验发现锁文件中 159 个 `registry.npmmirror.com` tarball URL 与注册表发布元数据不一致，依赖安装被阻止；因此本次未能复现 TypeScript 检查、Lint 或 Vite 构建。不能把旧文档里的“构建通过”视为当前基线实测。
3. `package.json` 未声明 `packageManager`，README 中 Vue/Vite/TypeScript 版本与当前锁定版本明显不一致，启动说明仍是芋道上游模板内容。
4. 仓库只提交 `.env.example`，旧报告所述 `.env.local` 不在当前快照；本地构建模式和生产变量生成规则未固化。
5. 工作台 7 日趋势仍用占位数据；代码读取不存在的 `summary.todayGenerated`，而统计卡使用的是 `aiJobsSucceededToday`，所以趋势的“今日”值也会落成 0。“进行中任务”待办还错误跳转到授权码页 `/zs/access-code`，实际 AI 任务页是 `/zs/ai-job`。
6. 业务页大量空 `catch {}`，会把鉴权、接口、数据合同等错误静默为无数据，增加联调误判概率。

**完成度判断**

- 业务页面与 API 接线：约 **85%～90%**。
- 可复验工程质量：约 **45%～55%**。
- 页面数量较完整，但在锁文件、构建、自动化测试和错误可观测性闭环前，不宜给出旧报告中的 95% 交付结论。

### 3.3 Java 后端

**已具备**

- 父工程为 Java 17 / `2026.08-SNAPSHOT`，当前启用 `dependencies`、`framework`、`server`、`system`、`infra` 以及 identity/design/commerce/ai-orchestration 四个众墅业务模块。
- 四个专项模块共有 32 个 Controller（19 app、12 admin、1 internal），代码中共发现 132 个类级/方法级映射注解。
- 众墅专项共有 16 个正向 Flyway 迁移文件，静态统计为 54 个 `CREATE TABLE` 和 38 个索引定义。
- 身份、点数账本、任务编排、候选/版本、预算、投稿审核、支付领域、Outbox、审计、导出等服务代码均存在；生产 PG profile 的密钥和默认值为空，开发便利开关默认关闭，安全默认方向正确。
- Controller 防空壳、PG 配置、Flyway、领域合同等测试源码均存在。

**未完成或不满足生产**

1. 可发现的真实适配器只有本地对象存储；微信身份、支付和内容审核均只有 Stub，实现中没有真实 AI Runtime/Provider。COS 适配器也不存在。
2. 支付领域已有通知处理服务，但没有可供支付渠道回调的 HTTP Controller；这与文档中“必须随真实验签同批上线”的计划一致，仍属于未交付项。
3. `application-pg.yaml` 默认关闭 AI 驱动器；在没有真实 Runtime 时，即使其它业务正常，AI 生成也不构成生产闭环。
4. 本机没有 JDK 和 Maven，也没有 Maven Wrapper；Docker 客户端存在但守护进程未运行。本次无法编译后端、执行 Testcontainers 合同测试或启动服务。
5. 当前树中 22 个专项测试文件含 129 个显式 `@Test` 方法；文档中的“151 个契约测试/全量全绿”没有随仓 runner 报告可复核。静态数量不等于实际执行数量，应以新 CI 报告重建口径。
6. `DefaultController` 暴露 `/test` 并记录请求参数、请求头与请求体。即使它是底座调试端点，也应在生产 profile 禁用，避免敏感头或请求体进入日志。
7. `AccountAdminController#getAccount` 用 `queryForObject(... LIMIT 1)` 读取最近点数流水；新账号没有流水时会抛 `EmptyResultDataAccessException`，后面的 `available == null` 兜底不会执行。
8. 后端目录保留 BPM、CRM、ERP、Mall、IoT 等大量上游模块，但父 POM 实际只启用 9 个模块。应明确“保留的上游源”和“本产品构建面”，避免扫描、升级和任务拆分把未参与构建的代码算入交付范围。

**完成度判断**

- 领域模型与 Stub 可运行链路：约 **80%～90%**。
- 真实外部集成：约 **10%～20%**。
- 生产交付准备：约 **55%～65%**。

## 6. 风险分级

### P0：进入正式多人开发前必须完成

1. **建立可追溯基线**：导入/保留三端历史，或补 provenance 清单、来源 tree hash、归档签字和基线 tag。
2. **建立根级 CI**：小程序测试、管理端依赖校验/type-check/lint/build、后端 JDK 17 编译与专项测试；所有任务以同一命令和 CI 状态验收。
3. **修复管理端依赖基线**：统一可信 registry，重新生成可验证 lockfile，声明 Node/pnpm 精确版本。
4. **归档可复跑 E2E**：把 37/37 脚本、fixture、环境初始化、期望结果和运行报告纳入仓库。
5. **修正文档证据链**：补齐或移除断链，归档视觉证据，确定唯一正本，重写与机器无关的启动说明。

### P0：真实内测/发布前必须完成

6. **小程序发布基线**：AppID、多环境 API 配置、生产禁用 `DEMO-ONLY`、素材迁移/分包、微信开发者工具与真机 17 页回归。
7. **真实身份和支付**：微信 code2session、支付预下单、回调验签/解密、查单、退款和重放测试。
8. **真实资产与合规**：COS 私有桶适配器、签名 URL/权限、内容审核、数据保留与删除策略。
9. **真实 AI Runtime**：冻结 D-11，落 Provider 适配器、超时/限流/重试/成本/回调合同，跑全链结算与退款回归。
10. **生产基础设施**：域名/ICP/HTTPS、PG/Redis、密钥托管、备份恢复、日志脱敏、监控告警和灰度回滚。

12. 修正管理端 AI 待办跳转、真实趋势接口、静默错误处理，并补组件/API/权限测试。

## 7. 建议的正式任务拆分

建议以以下工作流拆分，前四项优先并行，外部集成受凭据门禁控制：

| 工作包 | 目标 | 退出条件 |

## 8. 最终准入判定

- **可以进入任务拆分：是。** 领域边界、三端代码和缺口已经足够明确。
- **可以直接开始大规模并行功能开发：暂不建议。** 应先完成 T01/T02，并冻结唯一状态清单。
- **可以认定“可正式内测”：否。** 目前只有 Stub 内测依据；真实微信、包体、支付、AI、存储和内容审核未闭环。
- **可以认定“生产就绪”：否。** 生产集成、自动化证据、安全/压测/运维门禁均未完成。
