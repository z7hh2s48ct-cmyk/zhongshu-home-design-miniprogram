## 1. 拆分原则

1. **可验证优先于完成度描述**：以当前仓库可重复执行的命令和 CI 证据为准，不继承无法复跑的历史“全绿”结论。
2. **真实链路与 Stub 分开验收**：Stub 只证明业务合同和联调骨架，不证明微信、支付、AI、COS 或内容审核已经投产。
3. **任务边界可独立合并**：每项任务只覆盖一个明确问题域，必须有输入、输出、依赖和退出条件。
4. **外部决策先行**：AppID、商户号、COS、AI Provider、内容审核和域名备案单独跟踪，不让开发任务隐性等待。
5. **资金、安全和数据权限优先**：支付、点数、授权、资产访问、内部签名和日志脱敏的失败路径必须有自动化测试。

## 2. 状态与优先级

| 字段 | 取值 |
|---|---|
| 状态 | `READY` 可开工；`BLOCKED` 等输入；`IN_PROGRESS` 进行中；`REVIEW` 待验收；`DONE` 已通过；`CANCELLED` 已取消 |
| 优先级 | `P0` 阻塞正式协作或发布；`P1` 核心功能/质量；`P2` 体验优化；`P3` 可延后 |
| 工作量 | 以人日估算，包含实现、自测、评审修复和文档；不包含外部审核等待时间 |

## 3. 统一完成定义（Definition of Done）

所有代码任务同时满足以下条件才可标记 `DONE`：

- 代码、配置和迁移已进入独立分支，PR 只包含本任务范围。
- 相关单测/合同测试/集成测试已新增或更新，且本地与 CI 均通过。
- 不提交真实密钥、个人绝对路径、临时测试产物或仅在作者机器生效的配置。
- 对外 API、环境变量、迁移或运维行为发生变化时同步更新唯一正本文档。
- PR 描述写明：范围、验证命令、证据、已知风险、回滚方式、未测试项。
- 涉及支付、点数、授权、资产权限、内部 API 的任务必须增加失败、重复、越权和重放路径验证。
- 验收人不是实现人；P0 任务至少需要技术负责人和对应测试角色共同确认。
