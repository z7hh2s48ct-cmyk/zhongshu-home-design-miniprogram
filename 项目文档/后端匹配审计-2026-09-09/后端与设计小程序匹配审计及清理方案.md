# 后端与设计小程序匹配审计及清理方案

审计日期：2026-09-09。对象：当前工作区的 Java 后端、微信原生小程序和管理后台。此次交付为盘点与清理方案，未删除、修改业务源码，未变更数据库。

## 1. 结论与优先顺序

**后端的问题主要是“无关脚手架代码较多、真实服务适配未完成、部分字段和业务行为没有对齐”，不是大面积接口路径写错。建议先修业务合同，再清理旧模块，最后收缩基础设施。**

- 当前根 Maven reactor 有 **25 个 POM**，包含 4 个众墅业务模块及 system、infra、framework 等依赖。
- **16 个未启用的旧业务模块**保留了 **5,375 个 Java 主源码文件、427,573 行代码**（含注释、空行，约 16.1 MiB 源文件）。这部分是首批源码精简候选。它们已经没有进入当前根 reactor；删除源码的收益以降低维护负担为主，不能据此宣称服务内存或构建时间会同比下降。
- 扫描到众墅业务 **61 个 C 端、66 个管理端、5 个内部端点**。小程序 **51 个 API 封装的 HTTP 方法和路径都能对应后端声明**。这只证明路由存在，不代表请求字段、响应、鉴权和业务闭环全部匹配。
- C 端有 **10 个端点没有 api.js 封装**；其中 2 个素材 content 端点由上传/下载工具直连，另外 8 个是刷新令牌、偏好、客服、数据请求、重投等待接入能力。不能把这 10 个全部计为无用接口。
- 本轮已离线复现项目 ID 精度丢失、403 处理不一致；初轮还复现了订单展示问题，后期工作区增量已修复该项，复核结果单列为 M11。另有微信身份、支付、存储/审核、刷新令牌等后端缺口，应优先于大规模删目录处理。

扫描期间工作区持续新增个人记录页和结果恢复能力。本报告采用后期复扫结果：**28 条页面路由，个人方案/投稿/收藏/充值记录列表已存在，结果版本也已补充资产 ID**。不再沿用旧文档中“这些功能全部占位”的结论。精确扫描时间、接口位置与源码 SHA-256 见 [inventory.json](inventory.json)。这不是对线上部署版本的核验。

## 2. 审计方法与边界

核对链路为：`app.json → 页面/工具的 API 引用 → HTTP 方法和路径 → Controller/VO → Service/Port → SQL/迁移 → 管理后台消费者`。

同时读取根 POM、server POM 和活动子 POM，剔除 XML 注释后检查依赖；检查当前启用模块对停用业务包的 Java 引用。未发现当前活动 POM 对上述 16 个旧顶层业务模块的直接依赖；相关 Java 命中为启动 Banner 的缺失模块提示字符串，未发现业务 import。

范围限制：接口列表统计的是四个众墅模块，未将 system/infra 的通用端点混入 132 个业务端点；未对所有脚手架方法逐行做安全审计。未访问生产日志、数据库、微信商户或 AI Provider；未跑带数据写入的 E2E。因此“未发现消费者”是静态证据，不能替代线上访问观察，也不构成删表依据。

详细路由和模块计数见 [接口与模块盘点](接口与模块盘点.md)。复跑命令：

```powershell
node 项目文档/后端匹配审计-2026-09-09/inventory.mjs
node 项目文档/后端匹配审计-2026-09-09/reproduce.mjs
```
