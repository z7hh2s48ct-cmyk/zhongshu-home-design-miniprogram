## 一、涉及产品角色的决策点总览

以下决策点无法由技术侧单方面决定（涉及业务口径、转化路径或用户预期），需要产品角色逐条确认：

| # | 决策点 | 核心问题 | 影响端 | 建议优先级 |
|---|---|---|---|---|
| P1 | 预算明细展示数量/单价（见二） | 透明度与内部计价口径的边界画在哪 | 后端契约+小程序 | 高（信任问题） |
| P2 | 选择页双路径收敛方向（见三） | 恢复态体验向主路径看齐，还是保留独立大图选择页 | 小程序 | 高（体验一致性） |
| P3 | 预算单分享/导出载体（见四） | 转发卡片、导出图片、还是暂不做 | 小程序（+视觉） | 高（真实场景缺口） |
| P4 | 旧版区间测算下线节奏（见五） | 是否还有真实用户依赖 VAR1 区间 | 小程序+后端 | 中（依赖存量数据判断） |
| P5 | 参数编辑"保存"语义（见六） | 改文案（轻）还是改暂存-提交模型（重） | 小程序 | 中 |
| P6 | 建造地区在设计流程采集 | 地区选择放需求输入还是立面配置？必选还是可选？ | 三端（白名单+快照+UI） | 高（预算导入完整度的最后缺口） |
| P7 | 预算保存后的转化出口 | 是否加"咨询顾问/预约"类动作承接？ | 小程序+运营流程 | 中 |
| P8 | 正式报价的用户触达 | 管理端发布报价后，用户如何得知（现在需自己进结果页） | 小程序消息中心 | 中 |
| P9 | 命名统一 | "快速预算"（入口/页面标题）vs"参考预算"（结果页/按钮）是否统一 | 小程序 | 低 |

P6–P9 是流程评估中发现、但不在用户指定清单里的产品级遗留点，一并列出。P6 补充说明：占地/层数已随 `addff56` 自动导入，**地区是预算导入完整度的最后一个结构性缺口**——设计流程不采集地区，用户每次进预算都要手选一次（且换草稿要重选）。若确认采集，改动链为：设计输入 UI 加地区选择 → `DESIGN_KEYS`/需求快照白名单加 `regionCode`（后端）→ `fromSnapshot` 已在 FIELDS 内无需再改 → 预算端去掉必选手工引导。工作量约 1 天，风险低（快照链向前兼容）。

## 二、后端契约：预算明细展示数量（P1）

### 现状

- 公开预算 VO（`AppItemizedBudgetRespVO`）的 `lines[]` 只有 `lineId / optionLabel / status / amountCents`；`quantity` 与 `unitPriceCents` 只存在内部表 `budget_line`（含 `pricing_snapshot`）。
- 用户在明细页看到"门窗 ¥85,000"，但**不知道单价多少、按多少数量算的**，无法验算。
- 同一产品里，T14"我的当地单价"页（`getMyPrices`）**已经向用户展示了每个选项的基准价**和本人覆盖价。

### 矛盾分析

当初"公开层不含单价/数量"的设计意图是：不泄露内部计价规则（价格表结构、派生规则、加价逻辑）。但这个口径在两处已经被现实侵蚀：

1. T14 已暴露基准单价——"单价是秘密"的前提不再成立；
2. 数量根本不是平台资产——`BudgetCalculator.resolveQuantity` 的数量来源是 FOOTPRINT_AREA / BUILDING_AREA / ROOF_AREA / PROJECT_QUANTITY（门户口数、墙面面积等），**全部是用户自己输入参数的函数**，用户拿自己的参数本可手算，不展示只是增加了验算成本，没有保护任何东西。

因此剩余的实质决策只有一个：**单价要不要在明细行回显**（即金额=单价×数量的完整算式）。

### 方案对比

| 方案 | 内容 | 改动 | 风险 |
|---|---|---|---|
| A. 完整透明 | 明细行展示 数量 + 单位 + 单价 + 金额 | 后端公开 VO 加 `quantity`（含单位枚举）与 `unitPriceCents`；前端明细行布局改造；管理端报价详情同步口径 | 与既有安全设计冲突需复审；T14 已暴露基准价，实质增量可控 |
| B. 数量透明（推荐起步） | 明细行展示 数量 + 单位；单价去"我的当地单价"页查 | 后端 VO 只加 `quantity`；前端明细行副文案 | 极低：数量源自用户输入，无泄密面 |
| C. 维持现状 | 靠免责声明兜底信任 | 无 | 信任问题留存 |

### 推荐

**B 先行、A 视反馈跟进**。B 一天内可上线（后端投影 + 前端 `UNIT_LABELS` 已有现成映射）；A 因 T14 的存在增量风险有限，但展示格式（金额精度、单位对齐）值得与视觉一起做。

### 待产品确认

1. 是否接受完整单价回显（A）？
2. 数量展示单位口径：沿用 T14 的 `UNIT_LABELS`（平方米/米/个/套/户/项）？
3. 派生量（如窗户面积=建筑面积×0.25）展示派生值还是原始输入值？——建议展示派生值并在"测算说明"里注明派生规则，否则验算不上。

## 三、选择页双路径收敛（P2）

### 现状

- 主路径：生成完成后**不再跳选择页**，候选在 generating 页内联呈现，用户页内点"选它"，`nextStep` 直达下一环节（`generating.js` UX 整改注释）。
- 恢复路径：`project-resume.js` 的 `resumeAction` 映射中，`SELECT_FLAT → plane-select`、`SELECT_ELEVATION → elevation-select`——中断续接的用户看到的是**另一套 UI**（大图列表选择页）。
- 后果：两套选择交互并存、双份维护（两个页面约 500 行逻辑与样式）、体验割裂；`addff56` 刚清理了 elevation-select 的假推荐标签/死 CSS，但双路径本身仍在。

### 方案对比

**A. 收敛到 generating 内联（推荐）**

- 改法：`project-resume.js` 的 `SELECT_FLAT/SELECT_ELEVATION` 映射改为 `generating?stage=...`；`resume()` 已重建 `globalData.jobId`，轮询已完成任务会立即到 finished 态并内联呈现候选，与主路径行为完全一致。
- **必须配套**：generating 页 finished 态目前没有"重新生成"入口（原选择页有）。收敛后恢复态用户"不满意想重新生成"无路可走，需在 finished 态补一个次级"重新生成"按钮（复用 `generation-price.confirm` 扣点确认链）。
- 删除面：`plane-select`、`elevation-select` 两页从 `app.json`、`access.js BUSINESS_PAGES`、`native-project-structure.test.js` 页面清单中移除；相关测试更新。
- 工作量：约半天。风险：恢复流程回归——需覆盖 6 种 `resumeAction` 的路径测试。

**B. 收敛回独立选择页**：主路径生成完成 redirectTo 选择页。否决理由：放弃内联整改成果（渐进呈现、少一次跳转），且选择页刚被发现一堆问题，维护方向不对。

**C. 维持双路径**：零改动，但双维护成本永久化，且两条路径行为差异（如恢复态没有内联）会持续产生"不一致"类反馈。

### 待产品确认

1. 确认收敛方向为 A（恢复态与主路径同体验）；
2. 重新生成入口放 generating finished 态的哪个位置（候选区下方次级按钮即可）；
3. 是否保留"生成完成后先看大图再选"的诉求——若有，A 方案可在内联候选图上点击放大（`wx.previewImage`）满足，不必恢复独立页。

## 四、预算单分享/导出（P3）

### 现状

- 结果页/明细页**无任何转发或导出能力**。预算是典型的"拿去和家人/施工方商量"的决策材料，用户唯一手段是截屏——截屏会丢失精确金额切换态、免责声明（合规文案）和完整明细。
- 数据是私有会话态：接收者无法通过转发直接查看他人预算（受 `requireOwner` 保护，这是正确的）。

### 方案对比（微信生态内）

| 方案 | 内容 | 价值 | 工作量 |
|---|---|---|---|
| A. 转发卡片 | `onShareAppMessage` 返回项目名+总额+构成摘要卡片；接收者点开落到**自己的**预算页 | 告知/引流，不解决"给对方看" | 半天 |
| B. 导出图片（推荐主体） | Canvas 2D 绘制预算摘要卡（总额/构成/关键参数/免责声明/可选小程序码）→ 保存相册 | 真正解决"发给家人/施工方"；合规文案随图带走 | 1–2 天（含视觉稿） |
| C. PDF 导出 | 小程序端生成 PDF 需后端渲染 | 施工方归档偏好 | 3 天+，MVP 不推荐 |
| D. 维持现状（截图） | — | — | 0 |

### 推荐

**B 为主、A 顺带**（A 的实现成本极低且自带拉新属性）。B 的信息结构建议：项目/方案名、总额（万元+精确双档取精确）、主体/外装构成、参数摘要（占地/层数/地区）、生成时间、**免责声明必须入图**（"前期参考，最终以正式报价单为准"）、可选小程序码。

### 待产品确认

1. 导出图是否带小程序码（拉新 vs 干净版面）；
2. 金额口径：万元概览图还是精确金额图，或双版本；
3. 不完整预算（"已计价小计"态）是否允许导出——建议允许但图上明确标注"待补齐，非完整总价"。

## 五、旧版区间测算入口迁移（P4）

### 现状

- 唯一活跃入口在 budget/input 页 context-note 区，与"项目预算历史"并列暴露给所有 C 端用户；
- legacy 生成 `LEGACY_RANGE` 记录（VAR1 单方区间×面积），结果页只读渲染、不能保存；
- 新版分项预算流程已完整。对普通用户，"旧版"二字只制造"我该用哪个"的选择困惑。

### 方案对比

| 方案 | 内容 | 适用条件 |
|---|---|---|
| A. 入口下线、接口保留（推荐） | 删 input 页链接；legacy 页与后端创建接口保留（历史记录详情直达仍可用）；观察 30 天无新增后下线创建接口 | 近期新增 LEGACY_RANGE ≈ 0 |
| B. 降级迁移 | 入口移到 history 页页脚小字 | 仍有真实用户在用旧口径 |
| C. 维持现状 | — | 不推荐（困惑留存） |

### 判断依据（执行前先跑数据）

```sql
SELECT COUNT(*) AS total,
       COUNT(*) FILTER (WHERE created_at > now() - interval '30 days') AS last_30d
FROM budget_estimate WHERE model = 'LEGACY_RANGE';
```

`last_30d ≈ 0` → A；否则 B。

### 待产品确认

1. 确认 VAR1 区间规则是否还有业务依赖（如线下话术、渠道物料引用）；
2. 下线观察期长度（建议 30 天）。

## 六、参数编辑"伪保存"交互模型（P5）

### 现状

- parameters / body / exterior 三页的编辑（输入、picker、点选）**即时写入本机草稿**（storage）；
- 底栏"保存参数 / 保存并返回"实际只做校验 + 返回，**按钮语义与实际行为错位**；
- 没有"放弃本次修改"的路径：parameters 的"恢复导入值"是清到最初导入值（不是撤销本次编辑），body/exterior 的选择只能靠再点别的选项改回。

### 方案对比

| 方案 | 内容 | 工作量 | 风险 |
|---|---|---|---|
| A. 改文案 + 页面级撤销（推荐） | 按钮改"完成"；footer-hint 说明"修改即时保留在本机草稿"；onLoad 深拷贝草稿快照，加"撤销本次修改"（写回快照） | 半天 | 低 |
| B. 暂存-提交模型 | 编辑进内存，保存时 diff 写 storage；返回=放弃 | 2 天+ | 高：地区变更即时清 selections、"保存失败保留原值"等既有边界逻辑要整体重排，回归面广 |
| C. 维持现状 | — | 0 | 语义错位与误改焦虑留存 |

### 推荐

**A**。草稿本身是低风险本机态（真数据在服务端、预算生成有幂等），B 的收益配不上复杂度。若产品判断"撤销"非必需，A 还可以再减配为纯文案修正。

### 待产品确认

1. 是否需要显式"撤销本次修改"能力（决定 A 的完整版还是减配版）；
2. 按钮文案定稿（"完成" / "完成并返回"）。

## 七、落地顺序建议

按"用户价值 ÷ 改动风险"排序：

1. **二-B 明细展示数量**（1 天，低风险，直接回应信任问题）
2. **三-A 双路径收敛**（半天，中风险需回归恢复流）——建议与 1 同批出
3. **四-B 预算图导出 + 四-A 转发卡片**（1.5–2.5 天，需视觉稿）
4. **五 legacy 入口迁移**（先跑 SQL 看数据，改动本身半小时）
5. **六-A 保存语义修正**（半天）
6. P6 地区采集、P7/P8 转化与通知——产品给出方向后另行排期

以上除标注"待产品确认"的决策点外，1–5 的技术方案均已收敛到单一推荐，确认后可直接进入实现。
