> 审查日期：2026-09-05
> 审查方式：3 个独立评审代理并行审查全部 4 个业务模块 + infra 扩展 + 种子数据，对照《后端技术架构 V1.0》合同逐条核对

## 一、总体结论

**服务层（业务逻辑+数据库事务）完成度约 90%，HTTP 接线层完成度约 35%。** 核心业务规则（并发扣点、槽位结算、授权码一次性交付、投稿三态分离）全部实现且有真实 PostgreSQL 测试背书；但相当一部分已完成的服务**没有 HTTP 入口**（前端调不到），且存在 2 个资损级缺陷和 1 组系统性鉴权不一致。

```
已完成且有测试背书 ████████████████████░ 服务层 ~90%
可被前端调用到     ███████░░░░░░░░░░░░░░ HTTP 层 ~35%
```

## 三、发现的问题（按严重度）

### 🔴 Critical（资损/核心流程断裂，共 7 项）

| # | 问题 | 位置 | 影响 |
|---|---|---|---|
| C1 | **QUEUED 任务直接取消不退款**：`requestCancellation` 把 QUEUED 直接置 CANCELLED 终态，不走结算退款（合同要求"结算 0 个结果并全退"） | AiJobOrchestrationService:401 | 用户扣了点、任务没跑、钱不退 |
| C2 | **AI 链路无生产驱动器**：`validateQuarantinedResults`/`settle`/`completeCancellation`/`dispatchOnce` 全仓零生产调用方（只有测试在调），无 @Scheduled/Worker | ai-orchestration + infra | 扣点后任务永远 RUNNING、结果永远隔离、Outbox 永远 PENDING |
| C3 | **支付链路零 HTTP 入口**：建单/通知回调/查单/退款四个动作的服务方法存在，但对应 Controller 全是占位 `success(null)` | AppRechargeOrderController 等 | 前端无法充值（Stub 也不行） |
| C4 | **App 鉴权三套机制并存且不兼容**：identity/design 手写 Bearer 解析；commerce 用底座 `SecurityFrameworkUtils`（拿到的是 null）；`AppAccessCodeRedemptionController` 漏 `@PermitAll` | 跨模块 | 集成环境下点数/兑换端点 401 或 userId 为空 |
| C5 | **发布 AI 案例数据全错**：硬编码 `style_code='AI'`/面积 200；`creator_user_id` 写成 submissionId；授权记录的 asset_id 写 submissionId；不建 case_asset 关联（详情无图）；跳过 PUBLISH_PENDING | SubmissionReviewService:221-268 | 案例库被假数据污染 |
| C6 | **internal-api 无服务身份鉴权**：既没放行（Runtime 调用 401）也没签名校验，mTLS/签名代码为零 | AiJobInternalController | 合同 §7.4 完全未实现 |
| C7 | **DevDataSeeder 生产风险**：pg profile 默认 `seed-dev-data=true`（环境变量缺省即开）；明文授权码打日志；固定 ID 中途失败会让 Spring 启动崩溃 | DevDataSeeder + application-pg.yaml | 生产误部署即写入演示数据 |

### 🟡 High（功能缺口，共 8 项)

| # | 问题 | 影响 |
|---|---|---|
| H1 | 退款渠道返回 UNKNOWN 后无收口（无 queryRefund、无补偿），用户余额被永久锁死 | 资金卡死 |
| H2 | 支付补偿方法 `recoverPendingInbox/recoverHangingOrders` 无调度/无管理入口 | 通知丢失即永久 PENDING |
| H3 | refresh token 无刷新端点（合同也未定义）| access token 2 小时过期只能重走登录 |
| H4 | 受限会话（restricted）无统一执法点，各 Controller 人肉自律 | 越权面 |
| H5 | P5/P6/P7A/P7B 共 18+ 端点占位（AppDesignProjectController 8 个、AppSubmissionController 5 个、SubmissionAdminController 4 个、AppBudget/AppMessage 各 3 个等）| 前端 8 页调不通核心流程 |
| H6 | `promoteCandidates`（任务终态→候选晋升）无触发机制：AI 结算后不回调 design | 生成完成候选也不出现 |
| H7 | 消息白名单缺 4 类事件（任务失败/退款/支付异常/授权失效），这些用户通知静默丢失 | 通知缺口 |
| H8 | 幂等键未限定用户维度：跨用户同 Idempotency-Key 会返回他人任务 | 越权+资损边缘 |

### 🟢 Medium（质量债，摘要）

- AuditPort 仅 1 处消费（人工调点），AI 任务/导出/交付链路无审计
- `claim` 的 providerCode 硬编码 "stub"；RechargePaymentService 内 'STUB' 渠道字面量泄漏 3 处
- VALIDATING/SETTLING 状态位无人写入（状态机中间态未落地）
- 平面选择不支持换选（立面支持轮换，行为不对称）；多资产授权只冻结首个 grant
- 隐私同意/数据主体（§6.11）表建了但无服务层；向 AI Provider 传输前无同意拦截
- 预算未与 design_result_version 关联（合同 §6.8 要求）
- 0 个 Controller 层测试——这正是 25 个占位端点没被发现的根因

## 四、测试覆盖评价

**110+ 契约测试质量高**（全部真实 PostgreSQL 容器，覆盖并发/幂等/事务回滚/竞态），但有两个结构性盲区：

1. **全部是服务层直连测试，0 个 HTTP 层测试**——占位端点、@PermitAll 缺失、鉴权不一致这类问题测试全绿也发现不了（本次靠评审才发现）；
2. 各阶段关键缺口：投稿状态机仅 3 用例（太少）；QUEUED 取消退款、Outbox DEAD 恢复、多 Worker 并发结算、退款 UNKNOWN 无实现自然无测试。
