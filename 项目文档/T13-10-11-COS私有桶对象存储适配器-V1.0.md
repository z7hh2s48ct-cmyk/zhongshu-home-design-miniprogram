## 1. 目的与边界

- **目的**：P0 阶段资产存储由 `LocalObjectStorageAdapter`（本地文件系统）承载，供开发与自动化验证；`ObjectStoragePort` 合同（架构 §6.9/§10.5）要求真实上线时全部对象**只存私有桶**、读取一律经**短期下载预签名**、数据库不存长期签名 URL、客户端直传经**上传预签名**。本项在**不新增第二套同用途 SDK、不改端口、不改消费逻辑**前提下，落地真实 COS 实现 `CosObjectStorageAdapter`，满足 T13-11「预签名上传/存在与大小校验/对象读取/消毒回写/短期下载 ＋ 区分 404/权限拒绝/超时」，并以真实 MinIO 协议级实测证明兼容性（T13-10）。
- **边界（本文不声称）**：真实腾讯 COS 端到端验收需正式凭据（区域/私有桶/endpoint/受限 secret-id/secret-key），属 T13-15（§9）；前端直传（T13-12）、对象不可替换保护（T13-13）、各入口回归（T13-14）属后续子任务；本项**不改** `ObjectStoragePort` 接口、`AssetService` 消费逻辑、`LocalObjectStorageAdapter`（三者仅协同，§8）；本项**不在生产启用** `provider=cos`（无凭据；`zsdev` 默认 `local`、`pg` 刻意不声明 provider〔缺失即守卫快速失败、绝不静默降级 local〕，COS 键留空，切 `cos` 前由部署环境带外注入密钥、启动守卫校验，§3.4/§3.5）。

## 3. 实现

### 3.1 T13-10 兼容验证结论：复用 S3 SDK 底层、另写适配器（不复用 `S3FileClient` 封装）

T13-10 要求「验证私有 PUT/GET/HEAD、签名、region/bucket/endpoint；能复用即不新增 SDK」。核实 infra `S3FileClient`（底座通用文件客户端）后，判定其**封装语义**与 `ObjectStoragePort` 私有桶合同**四点不符**，故复用其**底层 SDK 依赖**（`software.amazon.awssdk:s3`，BOM 锁 2.54.7，**不新增第二套同用途 SDK**）、另写 `CosObjectStorageAdapter`：

| # | `S3FileClient` 封装 | `ObjectStoragePort` 私有桶要求 | 结论 |
|---|---|---|---|
| ① | `presignPutUrl` 用**固定 24h** TTL | 上传票据 **900s**、下载 URL **300s** 的**可配短 TTL** | 不符 |
| ② | **无 `headObject`** | `existsWithSize` 须在**不下载对象体**前提下校验大小 | 不符 |
| ③ | `getContent` 返回 `byte[]`（全量下载） | `getObject` 须返回 `InputStream`（流式，供大对象校验/消毒） | 不符 |
| ④ | **不暴露** 404/403/超时判别 | T13-11「区分 404、权限拒绝、超时，不将所有错误当不存在」 | 不符 |

- **`后端程序/yudao-module-design/pom.xml`（改，+8）**：`yudao-module-design-biz` 加 `software.amazon.awssdk:s3`（`main` 作用域）。**无 `<version>`**——版本由 `yudao-dependencies` BOM 统一管理（核实：`awssdk.version=2.54.7`、`<dependencyManagement>` 已声明 `software.amazon.awssdk:s3`），与 infra `S3FileClient` 同一 SDK 版本，**不新增第二套**。

### 3.2 T13-11 `CosObjectStorageAdapter`（`ObjectStoragePort` 真实实现，519 行）

装配条件 `@ConditionalOnProperty(prefix="zhongshu.design.asset.storage", name="provider", havingValue="cos")`，与 `LocalObjectStorageAdapter` **互斥**（每端口只装配一个实现，§5 `DevelopmentAdaptersContractTest` 实证）。五端口方法：

| 方法 | 实现 | 关键点 |
|---|---|---|
| `presignUploadUrl(key,ttl)` | `S3Presigner.presignPutObject`，`signatureDuration=ttl` | **不签名 Content-Type**（由客户端按申报 MIME 自设，与服务端策略解耦，T13-12 兼容前提）；本地计算无网络调用；**URL 属对象级承载凭据，绝不写日志** |
| `existsWithSize(key,size)` | `s3.headObject` 取 `contentLength` 比对 | **不下载对象体**；仅 404/NoSuchKey 返 `false`，403/超时/服务异常抛出（§4，T13-11 核心） |
| `getObject(key)` | `s3.getObject` 返 `ResponseInputStream`，再包 `ReadDeadlineGuardedInputStream` | **流式**（调用方负责关闭）；404 亦抛 `NOT_FOUND`（本应存在却读不到，如实暴露而非静默）；**响应体读取受累计预算守卫**（承 codex round-1 P2＋round-2 净化，见下方「有界超时（双层）」） |
| `putObject(key,bytes)` | `s3.putObject` ＋ `contentTypeFromKey(key)` | **消毒回写/管理端上传**；按 key 扩展名推断 MIME（`.jpg/.jpeg→image/jpeg`、`.png→image/png`、`.pdf→application/pdf`、else `octet-stream`），避免 SDK 默认 `octet-stream` 覆盖形象 MIME 致预签名 GET 内联展示异常 |
| `presignDownloadUrl(key,ttl)` | `S3Presigner.presignGetObject`，`signatureDuration=ttl` | 私有桶下**唯一读取路径**（无公开访问）；本地计算；**URL 绝不写日志** |

- **双构造器（承 `RealWechatIdentityAdapter` 惯例）**：`@Autowired public` 构造器（7 参经 `@Value` 从 `zhongshu.design.asset.storage.cos.*` 绑定）→ `buildS3`/`buildPresigner` → 委派**包级构造器**（`(S3Client,S3Presigner,bucket,readTimeoutMs)`，供隔离测试注入替身客户端与读取预算，如以 mock 确定性触发超时/慢滴）。多构造器并存故以 `@Autowired` 显式指明注入入口。
- **构造期校验快速失败**：`validateConfig` 校验 endpoint/region/secret-id/secret-key 非空白 ＋ endpoint 以 `http://`｜`https://` 开头，违例抛 `IllegalArgumentException`，**消息只回显配置键名、绝不回显密钥值**。
- **有界超时（双层）**：① `buildS3` 设 `ClientOverrideConfiguration.apiCallTimeout(max(1,ms))` 界定单次 S3 调用（含 SDK 内部重试）总时长，杜绝 COS 不可达时请求线程被无限挂起；② **响应体读取预算**（承 codex round-1 P2＋round-2 P1/P2）——`getObject` 返回的 `ResponseInputStream` 由嵌套 `ReadDeadlineGuardedInputStream` 包装：以 `System.nanoTime()` 累计截止（`readTimeoutMs`，公开构造器默认复用 apiCallTimeout 值）界定**完整读取**总时长，慢滴/停滞流在超预算时被 `abortQuietly()` **调 `abort()` 强制切断连接（不排空剩余响应体，区别于 Apache5 下会 drain 的 `close()`）** 并抛 `ObjectStorageException(TIMEOUT)`（**codex round-4 P1 修复**：`abort()` 内部调 `IoUtils.closeQuietlyV2(in, log)`，底层 close 抛异常时 SDK 会调 `Logger.debug(Supplier, Throwable)` 记录**该原始异常**（Supplier 只返回常量 `"Ignore failure in closing the Closeable"`，泄露载体是 Throwable 的消息/异常链，非 Supplier 内容）；`abortQuietly()` 的 catch **无法撤回 SDK 内部已执行的日志调用**，故此通道不靠适配器代码封堵，而靠 `logback-spring.xml` **显式**将 `software.amazon.awssdk`（含 `ResponseInputStream`）钉为 `INFO`——`Logger.debug(Supplier, Throwable)` 内部先判 `isDebugEnabled()`，有效级别 ≥ INFO 时 Supplier 不求值、Throwable 不交给任何 appender，**结构性关闭**且不依赖 root 默认级别（`logging.level.root=DEBUG` 即可绕过 root 默认，但绕不过显式声明的 logger 级别）；该加固由 `SdkLoggingHardeningContractTest` 锁定并经 mutation 实证有鉴别力（§3.6、§5 末）。`abortQuietly()` 自身仅 catch RuntimeException 确保异常不上抛）；`close()`/`available()` 亦净化（round-2 P1：`close()` 幂等＋异常只记类型名绝不上抛裸 IOException，杜绝其作 suppressed 附着或被 `AssetService` 误判 READ_FAILED；`available()` 异常返回 0）；单次停滞 `read` 由 SDK socket timeout 兜底，其 `SocketTimeoutException` 被包装流捕获净化为 `TIMEOUT`（`RuntimeException` 净化为 `SERVICE_ERROR`）。**净化异常绝不带 cause、绝不 `log e.getMessage()`（只记 `getClass().getSimpleName()`），杜绝签名 URL/凭据经响应体读取路径泄露**（apache5-client 为 `runtime` 作用域，main 代码不 compile 引用其 builder 配 socketTimeout，故纯包装流方案不改 pom）。
- **`S3Configuration`**：`pathStyleAccessEnabled`（MinIO/隔离测试 `true`；腾讯 COS 虚拟主机式 `false`，SDK 自动拼 `{bucket}.{endpoint}`）＋ `chunkedEncodingEnabled(false)`（与 infra `S3FileClient` 一致，规避 aws-chunked 流式签名在部分 S3 兼容端的兼容问题）。
- **`@PreDestroy close()`**：释放 `S3Client`/`S3Presigner` 连接池（均 `SdkAutoCloseable`）。

### 3.3 `ObjectStorageException`（分类异常，44 行）

- **四类根因 `Reason` 枚举**：`NOT_FOUND`（404/NoSuchKey）、`ACCESS_DENIED`（403/AccessDenied）、`TIMEOUT`（ApiCallTimeout/SdkClientException）、`SERVICE_ERROR`（其它 5xx 等）。
- **刻意继承 `IllegalStateException`**：与既有 `LocalObjectStorageAdapter` 以 `IllegalStateException` 表达存储失败的约定一致，令 `AssetService` 中既有的 `catch (IOException|IllegalStateException)` 消费点（`readReviewTicket`/`readCasePreviewTicket`）**无需改动**即可捕获 COS 存储失败，不破坏 T13-14 各入口回归（§8）。
- **安全**：消息只含 `objectKey`（存储路径，非凭据）与失败类别，**绝不含签名 URL、secret-key 或完整请求 URL**；构造时**不接收底层 SDK 异常作为 cause**（其消息可能回显含签名参数的请求 URL），根因只以「状态码 ＋ 错误码 ＋ 异常类型名」记录于服务端日志。

### 3.4 装配守卫登记：`RealServiceWiringPolicy`（+18/-4）

- `path-style-access`/`api-call-timeout-ms` **有安全默认值**（`false`/`20000`），非必填，**不登记**。
- **违例聚合一次抛出**，消息只回显键名/环境变量名（承既有守卫纪律）。
- javadoc/注释同步更新：预留的 B2 登记点落地；并注明 B2 COS 与 B4（微信支付）密钥键**均已登记**、后续新增真实服务按同构登记即可复用本校验（round-5 P3① 订正：原「B4 落地时追加」为未来时陈旧表述，与 HEAD 已完成登记不符，已改为「已登记」）。

### 3.6 SDK 与 HTTP 传输层日志级别加固：`logback-spring.xml`（改，+57）——codex round-4 P1 ＋ round-5 P1 修复

`abortQuietly()` 的 `catch` **无法撤回 SDK 内部已经执行的日志调用**，故 §3.2 所述 `abort()` → `IoUtils.closeQuietlyV2(in, log)` → `Logger.debug(Supplier, Throwable)` 泄露通道必须在**日志配置层**结构性关闭，而非依赖「root 默认 INFO」这一可被一个 `logging.level.root=DEBUG` 环境变量绕过的假设。**codex round-5 P1 进一步揭示第二条泄露面**：AWS SDK v2 2.54.7 默认同步传输层为 apache5-client（`buildS3()` 未覆写 httpClient 即用之），在 `root=DEBUG` 时经 `org.apache.hc.client5.http.headers`/`.wire` 逐个打印含 `Authorization`（`Credential=<secret-id>`、`Signature=`）的请求头且不脱敏——这两个 logger **不在 awssdk 命名空间下**，故须一并钉级别封堵（下表、§5 末锁定测试③）。

**加固前状态（实证）**：原 `logback-spring.xml` 仅有 `<root level="INFO">`、**零显式 `<logger>`**，即无任何针对 SDK 的级别约束。**有意不断言 root 级别**：本加固不依赖 root，故运维可将 root 调至 DEBUG 排查业务问题而不破坏加固——这正是显式钉级别相对「依赖 root 默认」的价值。

**已评估并否决的两个替代方案**：① **自定义 `ResponseTransformer` 完全绕开 `abort()` 泄露路径**——SDK 确有公开入口（`S3Client.getObject(req, ResponseTransformer)` 重载、`ResponseTransformer.transform(resp, AbortableInputStream)`、`FilterInputStream.in` 为 protected），故**并非「只能反射、无法绕开」**（round-5 P3③ 订正原不准确表述）；否决理由是**工程成本**——改用该重载须自行接管响应流完整生命周期（读取预算、abort/close 幂等、异常净化分类），把已由 `ReadDeadlineGuardedInputStream` 收敛的逻辑重铺一遍，改动范围与维护成本远大于「配置层钉级别 ＋ 契约测试锁定」；且泄露载体（SDK 内部 `debug(Supplier,Throwable)` 与 Apache 传输层 header debug）本就发生在适配器代码之外的 SDK/传输层，重写转换器并不能免除对传输层 logger 的级别约束。② **Logback TurboFilter / 编程式设级别**——代码耦合 Logback 具体实现、静态初始化副作用、测试环境无 Logback 时脆弱，比配置钉级别复杂且更易失效，否决。

## 4. 错误判别矩阵（T13-11 核心验收）

T13-11 明确「**区分 404、权限拒绝、超时，不将所有错误当不存在**」。`classify(op,key,S3Exception)` 只取 `e.statusCode()` 与 `e.awsErrorDetails().errorCode()` 记日志（**绝不 `log e.getMessage()`**——可能含带签名参数的请求 URL；**绝不带 cause** 外抛——经 `GlobalExceptionHandler` 落库会泄露 URL）：

| S3 端条件 | 判据 | `Reason` | `existsWithSize` | `getObject`/`putObject` | 语义 |
|---|---|---|---|---|---|
| 404 / `NoSuchKey` / `NotFound` | `isNotFound(e)`（statusCode==404 或 code∈{NoSuchKey,NotFound}） | `NOT_FOUND` | **返 `false`** | 抛出 | 确属不存在 |
| 403 / `AccessDenied` | `sc==403 \|\| "AccessDenied".equals(code)` | `ACCESS_DENIED` | **抛出** | 抛出 | 凭据无权访问，属配置/权限问题，**绝非「不存在」** |
| `ApiCallTimeout`/`ApiCallAttemptTimeout`/`SdkClientException` | catch 分支 | `TIMEOUT` | **抛出** | 抛出 | 瞬态、可重试，**绝非「不存在」** |
| 其它 `S3Exception`（5xx 等） | classify else | `SERVICE_ERROR` | **抛出** | 抛出 | 服务端侧问题，**绝不静默降级为「不存在」** |

**关键不变量**：`existsWithSize` **仅在确属 404 时返 `false`**——若把 403 权限拒绝或超时误判为「不存在」（返 false），会把**服务端凭据权限问题或瞬态故障**误判为**用户未上传**，令 `completeUpload` 错误地以 `SIZE_MISMATCH` 拒绝合法资产。故 403/超时/服务异常一律抛出，与 404 的 `false` 语义**严格区分**。`isNotFound` 双判（statusCode==404 **或** errorCode∈{NoSuchKey,NotFound}）——因 HEAD 404 无响应体、SDK 可能只给 statusCode=404，而 GET 可能给 NoSuchKey 错误码。

## 8. 与既有资产/装配逻辑的关系（未改，仅协同）

- **`ObjectStoragePort` 端口未改**：5 方法签名（`presignUploadUrl`/`existsWithSize`/`getObject`/`putObject`/`presignDownloadUrl`）不变，本项仅新增 `cos` 实现；`LocalObjectStorageAdapter`（P0 本地实现）保留，两者经 `@ConditionalOnProperty(provider)` **互斥装配**（§5 实证）。

  - **P2 包装流的 fail-loud 穿透语义（刻意设计，承 codex round-1 P2）**：`AssetService` 4 处 `getObject` 消费点分两类 catch——`readReviewTicket`/`readCasePreviewTicket` 为 `catch (IOException|IllegalStateException)`，`completeUpload`/`readForTicket` **仅** `catch (IOException)`。`ReadDeadlineGuardedInputStream` 在响应体读取超时/断连时抛 `ObjectStorageException`（属 `IllegalStateException`、**非** `IOException`）：① 被前两类捕获转友好提示；② **穿透** 后两类的 `catch (IOException)`，使 `completeUpload` 不把**瞬态读取超时**误判为 `READ_FAILED` → 资产永久 `REJECTED`，而是留在可重试的 `VALIDATING` 态。此即 P2 修复目标（避免瞬态故障永久拒绝合法资产），故**穿透是刻意的正确行为、非缺陷**。
