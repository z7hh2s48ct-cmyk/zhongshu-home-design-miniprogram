## B. 前端工程（`前端程序/`）需要新增的配置与代码

| # | 项 | 位置（建议） | 内容/取值 |
|---|---|---|---|
| B1 | **API 基础地址** | 新建 `miniprogram/utils/config.js`：`module.exports = { apiBase: 'https://api.你们域名', env: 'prod' }`；开发期可用 `http://本机IP:48080` + 工具勾选"不校验合法域名" | 全部请求的前缀 |
| B2 | **统一请求封装** | 新建 `miniprogram/utils/request.js`：封装 `wx.request`——自动带 `Authorization: Bearer <accessToken>`、`Content-Type: application/json`、401 时跳转 `pages/auth/index` 重新登录、非 0 `code` 弹 `msg` | 后端响应壳 `CommonResult{code,data,msg}`，`code=0` 成功 |
| B3 | **登录流程改造** | `pages/auth/index`（现无 wx.login）：调 `wx.login()` 拿临时 code → `POST /app-api/design/v1/auth/wechat-login` → 存 `accessToken/refreshToken`（`wx.setStorageSync`）→ `GET /design/v1/access-grant` 判断 `restricted` | 未兑换授权码的账号是**受限会话**：只能查准入状态/兑换授权码 |
| B4 | **token 注入** | B2 封装内读取 storage | 受保护接口全部要 Bearer |
| B5 | **Idempotency-Key 生成** | B2 封装或各提交页：创建任务/订单/投稿请求加请求头 `Idempotency-Key: <uuid>`（32 位随机） | 防重复点击重复扣点/建单 |
| B6 | **数据替换清单**（硬编码→API） | `wallet/recharge.js`（套餐数组）→ `GET /design/v1/recharge-plans`；`home/index.js`（精选/统计）→ `GET /design/v1/home`；`library/index.js`（户型列表）→ `GET /design/v1/cases`；`ai-design/generating`（进度轮询）→ `GET /design/v1/ai-jobs/{jobId}`；`messagecenter` → `GET /design/v1/messages` + `unread-count`；`profile/index` → `GET /design/v1/profile` + `point-account` | 逐页替换，每页按「加载/空态/失败重试/无权限」四态处理 |
| B7 | **appid 真值** | `project.config.json` → `appid`: A1 的值 | 否则真机无法运行、`wx.login` 拿到的 code 无效 |

## C. 后端部署（`ruoyi/ruoyi-vue-pro`）环境变量与配置

**C2. 专项密钥（生产必须由密钥托管/环境变量提供，缺失时相关接口明确报错）**

| 配置键 | 要求 | 用途 | 缺失后果 |
|---|---|---|---|
| `zhongshu.identity.access-code-pepper` | ≥32 字符随机串 | 授权码 HMAC 指纹 | 兑换/发码接口报错 |
| `zhongshu.identity.access-code-pepper-version` | 默认 `v1`，轮换时递增 | 指纹版本标记 | — |
| `zhongshu.identity.access-code-artifact-key` | Base64 的 32 字节 | INLINE/TICKET 批次授权码密文与单码复制 | 缺失时发码及授权码复制报错 |
| `zhongshu.identity.wechat-appid` | A1 的 AppID | 登录身份解析 | 登录身份与生产不一致 |
| `zhongshu.design.asset.storage-root` | 本地目录（P0）或接 COS 后换 | 资产对象存储（现为本地适配器） | 不配走默认临时目录 |
| `zhongshu.commerce.payment.merchant-id` | A4 的商户号 | 支付通道标识 | 走默认 stub-merchant |

## E. 联动顺序建议（依赖关系排序）

1. **后端先跑起来**：装 PostgreSQL+Redis → 配 C1 环境变量 → 以 `local,pg` profile 启动 → Flyway 建表 → 用 curl 打 `/app-api/design/v1/home` 确认响应壳。
2. **前端接骨架**：写 B1/B2（config+request 封装）→ 先接「首页/户型库」两个只读接口（不需要登录）验证通路。
3. **接身份链**：A1 AppID 就位 → B3 登录流程 → B4 token 注入 → 验证「受限会话→兑换授权码→升级正式」。
4. **接业务写链**：充值方案读取 → 建单（Stub 支付通道下 `reconcile` 可模拟支付成功）→ 生成任务全链 → 投稿审核（管理端）→ 发布。
5. **G0B/D-10 签字后**：A4/A5 商户凭据 → P8B 真实微信支付 Adapter → 换下支付 Stub。
6. **上真机前**：A3 合法域名 + B7 真实 appid + 关闭开发者工具的"不校验域名"。

## F. 当前差距汇总（联动的三道坎）

1. **前端没有网络层**：需要新写 config/request 封装与登录流（B1~B5），并把 17 个页面的硬编码数据逐页替换为 API（B6）——这是最大的工作量。
2. **后端未部署**：需要 PostgreSQL/Redis 环境 + C1/C2 配置；管理后台登录还需底座 system 库初始化（MySQL 或完成 PG 化）。
3. **微信凭据未申请**：A1/A3 是真机联调的硬前提；A4/A5 只影响真实收款（Stub 可先走通全业务流）。
