## 1. 目的与边界

- **目的**：T13-04/T13-05 已把微信身份解析（`resolveAccount`）与登录错误分类做实，但**账号解析在并发下的正确性**、以及它被 `AccessCodeRedemptionService#redeem` 复用时的**事务安全性**尚无真实数据库回归。本项以 Testcontainers 真实 PostgreSQL 补齐并发/归属回归，并在过程中发现 `resolveAccount` 的事务传播在 redeem 路径存在缺陷，予以最小修复。
- **验收四要点 → 落点**：

  | 验收要点 | 落点 | 归属 |
  |---|---|---|
  | 并发首登不重复建账号 | `uk_wechat_identity_appid_openid` 唯一键 + `resolveAccount` 的 `DuplicateKeyException` 复用路径；**本项修复其事务传播** | 承继既有 + **本项 T13-06 修复** |

## 2. 缺陷根因：PostgreSQL 嵌套事务中止（SQLSTATE 25P02）

「同一新微信并发直兑不同码」这一路径在**修复前确定性存在**一处缺陷。异常链：

```
UncategorizedSQLException: SELECT account_id FROM wechat_identity WHERE appid=? AND openid=? ...
    SQL state [25P02]; current transaction is aborted, commands ignored until end of transaction block
  at AccountLoginService.findAccountId
  ← AccountLoginService.resolveAccount（catch 后的重查）
  ← AccessCodeRedemptionService.redeemInTx（L98）
Caused by: PSQLException: duplicate key value violates unique constraint "uk_wechat_identity_appid_openid"
  at AccountLoginService.resolveAccount（INSERT wechat_identity）
```

**机制**：

1. `AccessCodeRedemptionService#redeem` 以 `txTemplate`（默认传播 `PROPAGATION_REQUIRED`）开启**外层物理事务**，在 `redeemInTx` 内先 `SELECT ... FOR UPDATE` 锁授权码行，再于 L98 调用 `accountLoginService.resolveAccount(...)`。
2. 修复前 `resolveAccount` 内部事务模板同为 `REQUIRED`，故**加入 redeem 的同一物理事务、共享同一 PG 连接**。
3. 多路并发解析同一新身份时只有一路 `INSERT wechat_identity` 成功；输家撞唯一键 `uk_wechat_identity_appid_openid` 抛 `DuplicateKeyException`。**在 PostgreSQL 中，任何语句错误会中止整个当前物理事务**（SQLSTATE 25P02），此后该连接上的任意语句（包括 `catch` 块里本应"重查复用赢家账号"的 `findAccountId`）都被拒绝、立即失败。
4. 结果：并发兑换中每一路输家都在重查处抛 25P02，外层兑换事务也无法提交——**同一新微信并发兑换将有一路以上报内部错误**。

> 根因不在唯一键冲突本身（那是并发首登的**预期**信号，`DuplicateKeyException` 复用路径正是为此设计），而在于**冲突发生在一个与调用方共享的物理事务里**：一旦共享事务被 25P02 中止，"冲突→回滚→重查复用"的恢复策略就无处立足。

## 3. 修复：`resolveAccount` 事务传播改为 `NESTED`（JDBC savepoint）

`后端程序/yudao-module-identity/.../account/AccountLoginService.java`（改）：账号解析专用事务模板 `resolveAccountTxTemplate` 的传播行为固定为 `TransactionDefinition.PROPAGATION_NESTED`。`DataSourceTransactionManager` 支持 savepoint 级嵌套事务，且其 `nestedTransactionAllowed` **默认即为 `true`**（无参构造器已调用 `setNestedTransactionAllowed(true)`），故 `NESTED` 开箱可用；本实现**不**从服务内部改动容器共享的事务管理器（codex round-2 P3-1：早期版本曾在构造期显式 `setNestedTransactionAllowed(true)`，实属冗余，且从服务构造器改动共享 bean 会波及其他 `NESTED` 调用方，已移除并删除对应 import；任何此类配置属配置层职责）。顺带删除一处**死代码** `private static class IdentityConflictException`（无引用，`git grep` 确认）。

**三方权衡（为何 `NESTED` 是唯一正确解）**——本方法会被 `AccessCodeRedemptionService#redeem` 在其外层事务内调用：

| 传播 | 冲突隔离 | 连接占用 | 无效兑换回滚 | 结论 |
|---|---|---|---|---|
| `REQUIRED`（加入外层） | ✗ 冲突中止**整个共享事务**（25P02），catch 重查立即失败、外层无法提交 | 同一连接 | ✓ 随外层回滚 | **原缺陷** |
| `REQUIRES_NEW`（独立物理事务） | ✓ 冲突只中止子事务 | ✗ **再占一个连接**：并发兑换各持外层连接+码行锁再等内层连接，在 Druid `max-active: 20` 上限下**连接池饥饿死锁** | ✗ 子事务**提前独立提交**，外层因 `ACCESS_CODE_ALREADY_CONSUMED` 回滚后账号仍残留（**破坏"无效兑换不落账号"**） | codex round-1 否决 |
| `NESTED`（savepoint） | ✓ 冲突只回滚到 savepoint 并**清除中止状态**，catch 重查得以成功 | ✓ **复用同一连接**，无池饥饿 | ✓ savepoint 是外层事务一部分，随外层一起提交/回滚 | **采用** |

- 经 `login`（无外层事务）调用时，`NESTED` 等价于新开事务，行为与原实现一致——故 `AccountLoginServiceTest`（8 用例）与 `IdentityP2AContractTest`（15 用例，含 20 路并发兑换）**零回归**（§6）。
- **隔离级别契约**：并发恢复依赖外层事务为 PostgreSQL 默认的 `READ COMMITTED`（重查取新快照，能看到赢家已提交的账号）；若调用方显式使用 `REPEATABLE READ` 等快照隔离，重查可能停留在旧快照而重抛冲突，此时应由调用方整体重试。当前所有调用方（`login` / `redeem`）均为默认 `READ COMMITTED`（codex round-1 P3-5 已记入方法 javadoc）。

## 4. 七场景回归（`AccountResolutionConcurrencyContractTest`，真实 PG）

新增测试类（`@Testcontainers` + `postgres:17-alpine`，Flyway `platform`+`identity`，走 `StubWechatIdentityAdapter`）。**难点**：仅靠并发时序无法确定性证明冲突恢复——竞争窗口内可能所有 worker 都走「已存在」快路径而不触发冲突（codex round-1 P2-3）。故设计为**三个确定性用例锁定 + 四个并发/归属用例端到端验证**，唯 `NESTED` 能全部通过：

| # | 场景 | 构造 | 断言 | 类型 / 作用 |
|---|---|---|---|---|
| 1 | 并发首登不重复建账号 | 16 线程同一 code `login` | 归属同一账号/openid；DB 仅 1 账号+1 身份；16 会话；全 `restricted` | 并发（`CyclicBarrier` 齐发） |
| 2 | 同身份归属一致、appid 隔离 | **受控适配器**编排：不同 code→同 `(appid,openid)`；相同 openid→不同 appid | 同身份恒同账号；异 appid 异账号；反查各得其所 | 归属（P3-7 精确 fixtures） |
| 3 | 激活流程并发幂等 | 10 线程各 `login`+`redeem` 同一码 | 同账号、1 条 ACTIVE 授权、1 兑换事实、码 CONSUMED、10 会话 | 并发 |
| 4 | 兑换服务并发解析账号 | 8 线程同一全新 openid 直兑不同码、无 prior login | 只 1 账号、1 ACTIVE 授权、8 兑换事实、8 码 CONSUMED、无一报错 | 并发（真实竞争端到端） |
| 5 | 被拒兑换不落账号 | fresh 身份兑**他人已消费**码 → `ACCESS_CODE_ALREADY_CONSUMED` | 新账号随外层回滚，`count(account)` 不变、`findAccountId` 为空 | **确定性排除 `REQUIRES_NEW`** |
| 6 | 外层事务内冲突后存活 | soft-deleted tombstone 令 INSERT 必撞唯一键（不依赖并发时序） | 外层事务 `SELECT 1` 仍成功；savepoint 回滚后无账号残留 | **确定性排除 `REQUIRED`** |
| 7 | 冲突后重查返回赢家账号 | 双连接编排：赢家持未提交唯一键，输家 INSERT 阻塞，`pg_blocking_pids(输家)` 命中赢家 pid 确认因果阻塞后放行提交 | 输家返回赢家账号、外层 `SELECT 1` 存活、无残留账号 | **确定性覆盖恢复主干**（补 round-2 P3-2） |

> **场景 5/6/7 的确定性锁定**：场景 5 在 `REQUIRES_NEW` 下必红（独立提交致 `count(account)=2`）；场景 6 在 `REQUIRED` 下必红——但失败点是冲突中止共享事务后 `resolveAccount` catch 内的重查 `findAccountId` **先**抛 25P02（并非测试外层的 `SELECT 1`，后者根本执行不到，codex round-2 P3-3）；二者确定性地证明唯 `NESTED` 同时满足"冲突隔离 + 随外层回滚"。场景 6 借 soft-deleted tombstone（唯一键 `uk_wechat_identity_appid_openid` 不含 `deleted`、而 `findAccountId` 只查 `deleted=FALSE`）**确定性**触发冲突，覆盖 catch 后"重查为空→重抛"分支；**场景 7** 再以双连接编排（赢家持未提交唯一键、输家 INSERT 阻塞、经 `pg_blocking_pids(输家)` 命中赢家 pid 精确确认「输家被赢家阻塞」后放行提交；round-3 P3-1 由全集群 `WHERE NOT granted` 收敛，杜绝误判无关等待者）**确定性**覆盖"重查命中赢家→复用"这条恢复主干，并断言恢复后外层事务仍可用——二者共同弥补场景 1/4 并发时序无法确定性触发冲突的不足（codex round-2 P3-2）。
>
> 验收要点「不同微信不能抢占已兑换码」「过期/撤销/已使用码返回明确结果」已由 `IdentityP2AContractTest` 覆盖（20 路并发单赢家、他人兑换拒绝 `1_070_000_003`、过期 `1_070_000_001`/停用 `1_070_000_002`、撤销实时生效），本类聚焦账号解析并发与归属，**不重复**该覆盖，二者互补构成 T13-06 完整回归。

## 5. 调用流可达性与已知局限（诚实说明）

- **经 HTTP API，原缺陷当前不可达**：`AppAccessCodeRedemptionController` 的兑换端点强制 `requireContext(authorization)` 校验 Bearer 会话，而会话只能由 `login` 创建；`login` 已先行 `resolveAccount`。故经 API 兑换时账号**必然已存在**，`redeemInTx` 内 `resolveAccount` 走 `findAccountId` 快路径，**不触发** INSERT，也就不会命中 25P02。
- **但 `redeem` 是 public 服务方法**：任何以**全新 openid** 并发直兑（绕过 login）的调用方都会命中缺陷——场景 4 正是此路径。作为可复用的领域服务，`resolveAccount` 必须在其契约支持的 `READ COMMITTED` JDBC 事务上下文中对任意调用方安全（隔离级别契约见 §3），不能依赖"上游恰好先登录过"这一编排巧合。本修复因此是**契约级健壮性根治**，而非修复一个当前终端用户可经既有 API 触发的线上故障；文档如实标注，不夸大。
- **HTTP 不可达的前提（codex round-1 P3-6）**：上述不可达性假设"登录后该 `wechat_identity` 持续存在且未删除"——token 校验查的是 `session`/`account`，并不复查 `wechat_identity`。当前无任何身份软删除的应用路径，故该假设在正常流程成立，但**非强制不变量**。
- **soft-delete 已知局限（P3-6）**：唯一键 `uk_wechat_identity_appid_openid` 涵盖已软删除身份，而 `findAccountId` 排除它们。若某身份被软删除，同 `(appid, openid)` 再次解析会撞唯一键、重查又为空，最终重抛 `DuplicateKeyException`（场景 6 固化了此行为）。这是**既有设计**（非本项引入），当前无删除路径触发；未来若引入身份注销，须显式定义 tombstone 处理（如返回领域级"身份不可用"错误），不得静默复活或改判归属。
