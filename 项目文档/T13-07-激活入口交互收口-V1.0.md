# T13-07 激活入口交互收口（小程序 auth 页）V1.0

日期：2026-09-10。所属批次：B1（微信身份与激活入口）。对应任务：T13 计划 §5 B1 表 T13-07。

验收标准（计划原文）：**首次输入激活码后内部识别微信再兑换；加载防双击；账号已激活则恢复使用；登录过期不误要求重复购买/兑换；不增加手机字段或独立登录按钮。**

本文是 B1 激活入口交互的**前端开发交付记录**，承继《T13-04 真实微信身份适配器》《T13-05 登录错误分类与一次性凭证处理》《T13-06 账号解析与激活码并发归属回归》的后端契约。它记录「小程序 `pages/auth/index` 已收口为内部识别微信→按需兑换，并对『已激活 / 身份过期 / 未激活 / 激活码错误 / 代际冲突 / 离页』诸态分流」的**前端实现与隔离测试证据（16 用例，全量 145 全绿，§6）**。

**本文不声称**：① 已在真机微信环境验收——真机验收属凭据依赖项，见 §9（对应 T13-09）；② 交互已「全部闭环」——离页后**在途**授权查询迟到 401 经 `request.js` 全局会话过期策略把用户拉回的**残余边界**，受「本项不改 `request.js`」所限未在激活页单独闭环，诚实记为已知限制、延后 T13-08（见 §2 末、§8）。codex 只读复审历程：round-1 GATE FAIL（3×P1+4×P2）、round-2 GATE FAIL（2×P1+3×P2），逐条核实均成立；round-3 修复后 codex 判 **GATE PASS（0×P1）**、五条验收全部满足，另列 4×P2：其中 **P2#1 是本项保留的运行时已知限制**（grant 已在途后离页的迟到 401 拉回，未闭环、延期 T13-08），P2#2/P2#3/P2#4（测试独立性/文档措辞/注释准确性）已于本轮精修，逐项处置见 §7.2 表、§7.3、§7.4。

## 1. 目的与边界

- **目的**：后端（T13-04/05/06）已把微信登录、错误分类、账号解析与激活码归属收口为稳定契约，但小程序激活页 `pages/auth/index` 改造前仍是**单一手动输码**路径——已激活账号一旦本地快照失效或会话过期落到本页，会被**误要求重新输入授权码**；加载态只有 JS 守卫、无视觉反馈。本项在**不改后端、不加手机字段/独立登录按钮**前提下，为激活页补齐**会话恢复分流**与**加载视觉态**，把「已激活 / 身份过期 / 未激活 / 激活码错误」收口到同一入口。
- **验收五要点 → 落点**：

  | 验收要点 | 落点 | 归属 | 测试 |
  |---|---|---|---|
  | ① 首次输入激活码后内部识别微信再兑换 | `verify`→`ensureLoggedIn`（内部 `wx.login`→`api.login`）→`redeemAccessCode`，无独立登录按钮 | 承继既有 | A2、B12 |
  | ② 加载防双击 | `verify` 的 `data.loading` JS 守卫（既有）+ 按钮 `is-loading`/`pointer-events:none` 视觉态（**本项新增**） | 既有 + 强化 | C16（+ activation-gate「兑换处理中防重复」） |
  | ③ 账号已激活则恢复使用 | `onLoad`→`recoverSession`：内部登录→`getAccessGrant`→`ACTIVE` 静默 `activate`（**本项新增**） | **本项新增** | A1、A4、A5 |
  | ④ 登录过期不误要求重复购买/兑换 | `recoverSession` 对身份过期（401）**强制重登一次**再查授权；对代际冲突（`SESSION_CHANGED`）**不强制重登**、按当前令牌/在途登录复用或正常登录后重查、**不在此主动清会话**；网络/服务端错误静默降级手动（**本项新增**） | **本项新增** | A5、B13、B14 |

- **边界（本文不声称）**：真机微信 `wx.login`、真实激活码兑换、真机激活往返归属需正式凭据（§9，属 T13-09）；本项**不改任何后端代码**、不改 `request.js` 的会话/刷新/`GRANT_REQUIRED`/`SESSION_CHANGED` 逻辑（仅消费其既有行为）、不改 `access.js` 的门禁判定（`requireActivation`/`protectedPage`）；`access.js` 唯一改动是 `navigate` 增加可选 `success/fail` 回调参数（向后兼容，见 §3.2）。

## 2. 设计决策：多态分流收口到单一入口

- **恢复放在进入页面（`onLoad`）**：验收③④要求「已激活则恢复」「过期不误要求兑换」。已激活/身份过期用户落到本页时**未必持有或记得授权码**，强制输码即违背验收。故 `onLoad` 先做**静默会话恢复**：内部重新识别微信（`ensureLoggedIn`，令牌有效则复用、不浪费一次性 code）→ `GET /access-grant` 查服务端授权真值 → `ACTIVE` 直接恢复并回到来源目标，**无需任何用户输入**。
- **授权真值以服务端为准**：恢复判定用 `api.getAccessGrant()` 的 `status`（后端 `AppAccessGrantController` 实时重判 `restricted`），**不**依赖本地 `v12Authorized` 快照——快照只是两次刷新之间的同步缓存（承继 `access.js` 既有原则）。这确保「撤销 grant 后恢复不误放行、已激活但快照丢失时恢复能救回」。
- **身份过期分流：401 强制重登 vs 代际冲突不强制重登（round-2 引入、round-3 修复 P1#1）**：`recoverSession` 的 `catch` 区分两类会话失效——
  - ① `err.code === 401`（身份过期；**并非**都等于「access+refresh 均过期」——也可能是刷新等待期已建立新会话后刷新返回 401、或 401 来自登录端点）→ `_recoverOnce(true)` **强制重新 `wx.login` 一次**再查授权。请求层对 401 清会话有**两条**路径：**①** 刷新失败分支——`refreshError.code===401` 且会话在等待期未变（`request.js:115` `getToken()===token` 且代际未变）→ `clearTokens`+`showActivation`；**②** 刷新成功后重放请求又 401（已 `retried`、有令牌，`request.js:121`）→ 同样 `clearTokens`+`showActivation`。**不清会话**的 401：**①** 刷新等待期会话已变（新令牌已建立，line 115 判否）→ 抛 401、保留新令牌；**②** 通过前置会话检查后 401 来自登录/刷新端点（`request.js:112`）→ 原样抛出、不清除现有会话状态（会话于请求期间已变则先进入 `request.js:99-105` 检查：命中 `:100-103` 同会话刷新轮换例外则重放一次，否则转 `SESSION_CHANGED`；`showActivation` 是否重定向还取决于当前是否已在激活页，`request.js:59`）。无论哪条，恢复层都**不**主动 `clearTokens`，仅强制重登一次；
  - ② `err.code === 'SESSION_CHANGED'`（本次恢复请求的会话**代际被并发操作改变**：可能已建立更新会话、也可能已被清除）→ `_recoverOnce(false)` **不强制重登**，按当前令牌/在途登录复用或正常登录后重查一次，**绝不在此主动 `clearTokens`**（否则二次 bump 代际、作废在途重试登录）。
  - round-2 曾对两类都执行 `http.clearTokens()` + 强制重登；但**代际冲突时清会话会二次 bump 代际、作废并发在途的重试登录**，令其登录响应同样被判 `SESSION_CHANGED`、令牌终空、兑换与导航零次（codex round-2 P1#1，已由 §6 B14 真实请求层回归锁定，并经临时回退实证该用例确有鉴别力）。其余失败（网络/500 等与身份无关错误）静默降级到手动输码，**不清会话、不弹 toast、不导航**。
- **合并在途登录（round-2 修复 P1-2）**：`recoverSession` 与手动 `verify` **相互独立**（恢复不用 `recovering` 门控 `verify`，避免与既有「页面创建后同步 `verify`」时序冲突），但二者共享 `ensureLoggedIn` 的**在途登录 Promise**（`this._loginFlight`）。无令牌时并发触达只发起**一次** `wx.login`，两条路径等待同一登录落定；登录成败都释放在途以允许失败重试。这杜绝了 round-1 缺陷——两次独立 `wx.login` 会使第二次登录响应被 `request.js` 判为 `SESSION_CHANGED`，破坏首次兑换。round-3 的 `SESSION_CHANGED` 分支正是**复用**该在途登录（`ensureLoggedIn(false)` 命中 `_loginFlight`），故重查授权与并发重试登录收敛到同一次登录。
- **`activate` 收口：幂等 + 在途守卫 + 导航成功才置终态 + 手动导航失败提示（round-2 修复 P2-2、round-3 修复 P2#2）**：恢复成功与手动兑换成功可能并发触达 `activate`。`this._activating` 作**在途守卫**防重入；`this.activated` **仅在 `navigate` 的 `success` 回调**置位——`fail` 回调释放 `_activating`、**不**置 `activated`（允许本页重试导航），并**在手动（非 `silent`）路径补回 `access.navigate` 原 `navigationFailed` 的『页面打开失败，请重试』提示**（round-2 的 `fail` 回调曾替换掉该默认提示、只释放锁，令手动兑换导航失败时只弹『激活成功』而无失败反馈——codex round-2 P2#2）；`silent` 恢复路径导航失败保持静默。授权写入失败仍留在本页可重试（承继既有语义，`silent` 时不弹 toast）。
- **离页失效：导航前复查 + 发起授权查询前复查（round-2 修复 P2-1、round-3 收窄 P2#1）**：`onUnload`/`continueBrowsing` 置 `_leftPage=true`；`_recoverOnce` 在**登录落定后、发起 `getAccessGrant` 前**复查 `_leftPage`（离页则不再发起授权查询，返回 `null`），并在**导航前**复查（杜绝迟到 `ACTIVE` 仍 `redirectTo`）。
  - **已知限制（诚实记录，延后 T13-08）**：若用户在授权查询**已在途后**才离页，该请求迟到 401→刷新失败时，`request.js` 会在页面层 `catch` 之前执行 `showActivation()`→`redirectTo('/pages/auth/index')` 把用户拉回。此副作用位于 `request.js`（本项**不改** `request.js`），是全局会话过期策略，激活页无法单独抑制。round-3 的**登录阶段复查已收窄窗口**（登录 = `wx.login` + 一次 POST，是较大的离页窗口，§6 B15 锁定「登录阶段离页不再发起授权查询、不被拉回」）；grant 已在途的残余边界延后 **T13-08 会话一致性**统一处理（为恢复请求隔离离页后的导航副作用）。

## 3. 实现

### 3.1 `pages/auth/index.js`（改）

- **`onLoad`**：解析 `target` → `_leftPage = false` → `setData({ accessReady:true })` → `this._recovery = this.recoverSession()`（`_recovery` 仅供测试确定性等待，生产不消费）。
- **`onUnload`（新增）**：`_leftPage = true`。
- **`ensureLoggedIn(force)`（改）**：`if (!force && http.getToken()) return Promise.resolve()`；`if (this._loginFlight) return this._loginFlight`（合并在途）；否则 `wx.login`→`api.login`→`http.setTokens`，把在途存入 `this._loginFlight`，成败均清空以允许重试。`force` 为真时忽略既有令牌强制重登（身份过期恢复用）；`force` 检查在 `_loginFlight` 检查**之前**，故 `force` 时若有在途登录仍复用（不重复 `wx.login`）。
- **`recoverSession`（新增，round-3 改）**：`if (this.recovering || this.activated || this._leftPage) return Promise.resolve()`；`_recoverOnce(false)`；`catch` 中——`err.code===401` → `_recoverOnce(true)`（强制重登）；`err.code==='SESSION_CHANGED'` → `_recoverOnce(false)`（**不强制重登**，按当前令牌/在途登录复用或正常登录后重查，**不**主动 `clearTokens`）；其余 → 静默返回；末尾 `recovering = false`。**round-2 的 `isSessionInvalid(err)` 合流判定与其内的 `http.clearTokens()` 已移除**（该合流正是 codex round-2 P1#1/验收④ 所指「身份过期与旧请求代际失效混同」）。
- **`_recoverOnce(force)`（新增，round-3 改）**：`ensureLoggedIn(force)` → **复查 `_leftPage`/`activated`（离页则返回 `null`、不发起查询）** → `api.getAccessGrant()` → 当 `!_leftPage && !activated && grant.status==='ACTIVE'` 时 `activate(this.target, { silent:true })`。
- **`activate(target, options)`（改，round-3 改）**：`silent = !!(options && options.silent)`；`if (this.activated || this._activating) return`；`_activating = true`；`wx.setStorageSync('v12Authorized', true)`（失败：`_activating=false`，`silent` 时不弹 toast 并 `return`）；`refreshFromServer()`；非 `silent` 弹「激活成功」；`navigate(target||HOME, true, { success:()=>{ activated=true; _activating=false }, fail:()=>{ _activating=false; if(!silent) 弹「页面打开失败，请重试」 } })`。
- **`verify`（未改）**：`loading` 守卫 → `ensureLoggedIn()` → `redeemAccessCode` → `status==='ACTIVE'` 才 `activate(this.target)`，失败 `toast(err.msg)`；因共享 `_loginFlight`，与恢复并发时不产生第二次 `wx.login`。一次性 code 语义天然满足：登录失败不写令牌，重试必取**新** code（承继 T13-05 §6）。
- **`continueBrowsing`（改）**：先 `_leftPage = true` 再 `wx.navigateBack({ fail: returnHome })`。

### 3.2 `utils/access.js`（改，round-2）

`navigate(url, replace=false, handlers={})` 增加第三参 `handlers`：`wx[method]({ url, success: handlers.success, fail: handlers.fail || navigationFailed })`。向后兼容（既有调用不传第三参时行为不变），供 `activate` 感知导航成败以决定是否置终态 `activated`。**round-3 未再改 `access.js`**；门禁判定（`requireActivation`/`protectedPage`/`leaveRestrictedPage`/`isAuthorized`）与 `refreshFromServer` 均未改。

### 3.3 `pages/auth/index.wxml`（改）

主按钮由静态 `<view class="v12-primary-button" bindtap="verify">激活并继续</view>` 改为加载感知：`class="v12-primary-button {{loading ? 'is-loading' : ''}}"`、文案 `{{loading ? '激活中…' : '激活并继续'}}`。**未新增任何手机号输入框或独立登录按钮**（验收⑤）。

### 3.4 `pages/auth/index.scss`（改）

新增 `.v12-primary-button.is-loading { opacity: 0.6; pointer-events: none; }`——加载态降透明 + 禁用点击，与 JS `loading` 守卫形成双重防双击。

## 4. 多态分流表

| 用户实际状态 | 进入激活页的行为 | 是否需输码 | 结果 |
|---|---|---|---|
| 已激活（服务端 `ACTIVE`），本地快照失效但令牌有效 | `recoverSession` 复用令牌→查授权→`ACTIVE` | **否** | 静默恢复 + 回到来源目标 |
| 身份过期（access+refresh 均失效，账号已激活） | 首查触发 401→刷新失败（会话于刷新等待期未变）→`request.js` 自行清会话；`recoverSession` 捕获 **401**→**强制重登一次**→重查授权→`ACTIVE` | **否** | 静默恢复，不误要求兑换 |
| 恢复请求的会话代际被并发操作改变（`SESSION_CHANGED`，如兑换/重试登录已 bump 代际） | `recoverSession` 捕获→**不强制重登**，按当前令牌/在途登录复用或正常登录后**重查一次**授权（**不**主动清会话） | 视当时会话授权 | `ACTIVE` 则静默恢复；否则静默降级，**绝不破坏并发在途重试登录** |
| 未激活（服务端 `NONE`） | `recoverSession` 查到非 `ACTIVE`→静默返回 | **是** | 停留手动输码→`verify`→兑换 |
| 激活码错误/过期/已被使用 | `verify` 兑换失败 | 是（重试） | `toast` 后端 `err.msg`，保留授权码可重试 |
| 恢复链路失败（`wx.login`/网络/500，非身份过期） | `catch` 静默降级 | 是 | 停留手动输码，不弹恢复错误、不清会话 |
| 恢复中用户离页（`onUnload`/继续浏览） | `_leftPage=true`；**发起授权查询前**与**导航前**均复查 | — | 登录阶段离页→不再发起授权查询、迟到的 `ACTIVE` **不再导航**（残余：grant 已在途后离页的迟到 401 拉回见 §2 末已知限制→T13-08） |

## 6. 隔离测试（无真机、`node --test` 即运行）

新增 `前端程序/tests/auth-recovery.test.js`（**16 用例，全绿**），复用 VM 加载器直接驱动 `pages/auth/index.js`。两种驱动模式：

- **A) API-mock（11 用例）**：覆写 `api.login/getAccessGrant/redeemAccessCode`，**不注入 `wx.request`**（令 `access.refreshFromServer` 静默跳过，与 `activation-gate` 环境一致），隔离激活页自身逻辑：
  1. 已激活静默恢复（默认首页/Tab 目标 `switchTab`、非 Tab 带参目标 `redirectTo` 三形态，断言 `redeemAccessCode` **零调用**、导航恰一次）；

## 8. 与既有门禁/会话逻辑的关系（未改，仅协同）

- `access.js` 的 `requireActivation`/`protectedPage`/`leaveRestrictedPage` 门禁**未改**：业务页仍以本地快照判权、失效即引导至激活页；本项只在激活页**内部**补齐恢复，使「已激活但快照失效」的用户落到激活页后被静默救回，而非被迫重新输码。
- `request.js` 的 401→refresh、`GRANT_REQUIRED`→`showActivation`、`SESSION_CHANGED` 代际保护**未改**：恢复链路复用其既有会话行为。身份过期（401）时 `request.js` 清会话有**两条**路径——**①** 刷新失败分支（`request.js:115` `refreshError.code===401` 且 `getToken()===token` 且代际未变）、**②** 刷新成功后重放请求又 401（已 `retried`、有令牌，`request.js:121`）——两者均 `clearTokens`+`showActivation`（并因当前正处于激活页 `pages/auth/index` 而**不**重定向，`request.js:59`）；若刷新等待期已建立新会话（迟到刷新 401 使 line 115 判否、保留新令牌）、或通过前置会话检查后 401 来自登录/刷新端点（`request.js:112`，原样抛出、不清除现有会话状态），则**不清会话/不导航**。`recoverSession` 无论哪条都**仅**强制重登、**不再重复** `clearTokens`；代际冲突（`SESSION_CHANGED`）表示并发操作已改变会话代际（可能已建立更新会话、也可能已被清除），`recoverSession` **不强制重登**、按当前令牌/在途登录复用或正常登录后重查、**绝不主动清会话**（round-3 修复 P1#1，纠正 round-2「两类都清会话」的有害行为）。
- **唯一残余（诚实记录，延后 T13-08）**：离页后**在途**授权查询迟到 401→刷新失败触发的 `showActivation`→`redirectTo('/pages/auth/index')`，属 `request.js` 全局会话过期策略，激活页无法单独抑制。round-3 的登录阶段复查（B15）已收窄窗口；grant 已在途后离页的拉回边界，需在 T13-08 为恢复请求隔离离页后的导航副作用（如请求级 `silent`/`abort` 或页面代际标记）方能完全闭环。
