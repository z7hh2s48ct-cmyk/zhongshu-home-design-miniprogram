## 0. 结论摘要

| 维度 | 结论 |
|---|---|
| 后端领域层 | **强**。54 张表、11 组可逆迁移、121 个真实 PostgreSQL 合同测试，事务与幂等设计达到生产水准 |
| 后端 API 层 | **半成品**。90 个端点中 **46 个（51%）仍是返回 `null`/空集合的 P1A 空壳** |
| 前端 | **接了 API 但链路断裂**。17 页均有 API 引用，但 AI 设计主链在"选择方案"处断开，无法走通 |
| 管理后台 | **0%**。12 张效果图已交付，代码工程完全不存在 |
| 实测质量 | 后端 121 测试 **1 个错误**（生产代码 NPE）；前端 22 测试 **4 个失败** |
| 可演示性 | 首页/户型库/激活/消息可通；**充值、我的、AI 设计、预算、投稿全部拿不到真实数据** |

**一句话判断**：这是一个"地基优秀、一楼没砌完就贴了外墙"的项目。领域内核质量远高于行业平均，但 P5～P8A 各包只交付了 Service 层，控制器接线被反复推迟到"下一个包"，最终没有任何一个包认领，导致前端联调建立在空壳端点之上。

### 2.1 已完成的工作（客观清单）

**后端领域层（高质量，可直接进入生产的部分）**：

1. **授权码体系**：128bit 熵 Crockford Base32 生成、HMAC-SHA-256（版本化 pepper）指纹、INLINE/TICKET 互斥交付、AES-256-GCM 制品加密、掩码显示、20 路并发单赢家、跨 AppID 隔离。9 个真实 PG 测试全绿。
2. **点数账本**：条件 UPDATE 行锁原子扣减、只追加流水、`available + reserved = 初始值 + Σ流水` 不变量、7 种流水类型、幂等键竞态恢复、双人复核调点（`maker != checker`）。12 个测试全绿。
3. **AI 任务编排**：`FOR UPDATE SKIP LOCKED` 多 Worker 领取、租约过期重领、递增 fencing token 拒绝陈旧回写、结果事件 durable inbox 幂等、隔离区二次校验、`decisionSeq` 单调序裁决取消竞态。
4. **结算规则**：0 有效全退 / 1~N-1 差额退 / N 成功 / N+1 封顶不多收，`settlementVersion + reason` 唯一，累计退款 ≤ 原扣点。8 个测试覆盖崩溃注入与重放。
5. **支付领域**：支付事实与到账事实双状态分离、通知 Inbox 先落库、主动查单补偿、整单退款预留→冲正三态处置。9 个测试，含"同订单重复受理致渠道重复打款"的 Critical 修复回归。
6. **上传安全**：魔数校验、像素炸弹守卫（守卫失败绝不解码）、EICAR 检测、EXIF 剥离留痕、ImageIO 重编码、三段式短事务 + CAS 固化、一次性下载票据 + 授权实时复查。
7. **案例目录**：不可变版本行、稳定游标分页（面积+ID）、下架即时不可见、批量逐项隔离。含 3 个 Critical 评审修复的回归测试。
8. **工程纪律**：11 组迁移全部配套 undo 脚本；每次提交写明 `Tested`/`Not-tested`/风险/回滚；错误码分段注册并有 `ZhongshuErrorCodeRegistryTest` 守卫。

## 四、代码质量问题（分级）

### 🔴 CRITICAL

**C-1｜`completeCancellation` 恒抛 NPE，AI 任务取消功能完全不可用**

`yudao-module-ai-orchestration/.../AiJobOrchestrationService.java:419,435`

```java
Map<String, Object> job = jdbcTemplate.queryForMap(
        "SELECT status FROM ai_job WHERE id = ? FOR UPDATE", jobId);   // 只查 status
...
if (updated == 1) {
    long jobOwner = ((Number) job.get("user_id")).longValue();          // user_id 恒为 null → NPE
```

- **失效场景**：用户点"取消生成"→ 无在途结果 → `updated == 1` → NPE → 事务回滚 → 任务永久卡在 `CANCEL_REQUESTED`，扣掉的设计点不退回。
- **引入来源**：`211f5098cc`（P7B，16:01）为 Outbox payload 补 `userId` 时，`requestCancellation` 改了 SELECT，`completeCancellation` **只改读取没改 SELECT**。
- **为何没被拦住**：该提交声明 `Tested: design 全模块 44 测试全绿`——**只回归了 design 模块，没回归被自己改动的 ai-orchestration 模块**。CLAUDE.md CI/CD 门禁第 2 条"运行完整的相关测试套件"被跳过。
- **附带问题**：同处 payload 硬编码 `"stage", "before-claim"`，而 `completeCancellation` 发生在 claim 之后，语义错误。

**C-2｜生产 profile 密钥与种子数据 fail-open**

`yudao-server/src/main/resources/application-pg.yaml:31-38`

```yaml
seed-dev-data: ${ZS_SEED_DEV_DATA:true}          # ← 默认 true
access-code-pepper: ${ZS_ACCESS_CODE_PEPPER:dev-only-pepper-0123456789abcdef-0123456789}
access-code-artifact-key: ${ZS_ACCESS_CODE_ARTIFACT_KEY:ZGV2LW9ubHktYXJ0aWZhY3Qta2V5LTMyLWJ5dGVzISEh}
dev-content-endpoint: ${ZS_DEV_CONTENT_ENDPOINT:true}
```

- `pg` 是**生产唯一的数据库 profile**。忘记设 `ZS_SEED_DEV_DATA=false` → 生产库写入测试授权码，且 `DevDataSeeder:114` 把**明文授权码打进日志**。
- P2A 提交与《联调清单》C2 均声明"缺失时兑换/发码接口快速失败"。加了 dev 默认值后**这条安全属性已失效**：pepper 缺失不再报错，而是静默使用已提交进 Git 的公开值——授权码 HMAC 指纹形同虚设。
- **引入来源**：`76752f91dd`（最后一次提交）。

**H-2｜AI 设计主链在"选择方案"处断开**

- `plane-select.js:24` 注释 `// 模拟候选加载（真实实现需要 promoteCandidates 端点）`，用 `setTimeout` 造 A/B 两个假方案；`api.getAiJob` 的返回值除了关 loading 外**被完全丢弃**。

**H-3｜`result.js` 未声明变量赋值，严格模式下必抛 ReferenceError**

`pages/ai-design/result.js:11`

```js
"use strict";              // 文件头
...

```

严格模式下给未声明变量赋值抛 `ReferenceError`。`loadVersions()` 由 `onLoad` 直接调用且无 try-catch → **最终方案结果页一打开就报错**。

**H-4｜前端授权门禁不接服务端授权态**

`utils/access.js:22` 仅读本地 `v12Authorized`。后台撤销授权后本地开关不变，用户仍可进入业务页（虽然后端会拒绝，但产品文档《09》§3.5 与 §4 明确要求前端按服务端判定降级）。`GET /access-grant` 已实现且前端 `api.js` 已封装 `getAccessGrant`，**从未被调用**。

## 七、总体评价

**领域内核（P1A～P4C、P3A/P3B）质量显著高于同类项目**。事务边界、幂等键、乐观锁、fencing token、Outbox、崩溃注入测试这些通常在"后期出事故才补"的东西，这里是在第一版就设计并验证了的。121 个测试全部跑真实 PostgreSQL 而非内存库，这一条就排除了绝大多数"测试通过但生产炸"的场景。

**问题集中在交付的最后一公里**。P5～P8A 每个包都把控制器接线推迟到"下一个包一起挂"（P5 推给 P6，P6 推给 P7，P7A 推给 P7B，P7B 推给"部署阶段"），最后没有任何一个包认领，形成了 46 个空壳端点。前端随后基于这些空壳做了"联调"，并在文档里记为已完成——**这是本项目当前最大的风险：完成度的账面数字与可运行的现实之间存在系统性偏差**。

好消息是：这个缺口的修复成本远低于它看起来的样子。服务层是真的完成了、真的测过了，接线是机械劳动。真正需要从零开始的只有管理后台。
